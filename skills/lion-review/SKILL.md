# 검수

끝난 결과물을 작성에 끼지 않은 실행이 한 번 검수하고, 고친 뒤 그 지적만 다시 보고, 남은 것은 위로 올린다.

## 바로 할 일

1. 주 세션이 직접 끝낸 바로 크기의 일(한두 파일, 보안·데이터 삭제·저장 형식·설치와 권한 설정·배포가 아님)과 서브 하나가 읽고 요약해 온 맡김 크기의 일은 검수자를 두지 않는다. 바뀐 동작을 실제로 돌려 보거나 결과 파일을 열어 확인하고 끝낸다.
2. 검수는 작업 끝에 한 번, 작성에 끼지 않은 같은 AI 의 별도 실행이 한다. 단계마다 끼우지 않는다. 다른 회사 AI 는 사용자가 원할 때만 읽기 전용으로 부른다. 사용자가 이 대화 밖에서 만든 결과를 검토해 달라고 하면 지금 실행이 검수자가 된다.
3. 검수자에게 원래 요청, 확정 결정, 기준 판본, 실제 변경·출력, 시험 결과, 작업에 쓴 스킬의 SKILL.md 경로, 규칙 문서가 가리키는 검수 기준 문서(있을 때), 읽기 범위, 시간 한도를 주고 "문제를 찾아라, 못 찾으면 본 범위를 대라" 꼴로 맡긴다. 만든 쪽의 결론과 자평은 주지 않는다. 맡기기 전에 기준 판본이 열리고 변경이 비어 있지 않은지 본다.
4. 요청·결정 자료가 없으면 커밋 메시지의 이슈 번호, 사용자가 준 경로, docs·specs 아래 명세 순으로 찾고, 없으면 사용자에게 묻는다. 끝내 없으면 요구 대조는 「요구 자료 없음」으로 적고 코드에서 요구를 지어내지 않는다.
5. 검수자는 읽기만 하고 다른 검수자를 띄우지 않는다. 대상 원문을 직접 열고 반례를 하나 이상 시도한다. 확인은 실물로 한다. 실제로 돌리고 실제 값과 실제 변경을 읽는다. 만든 쪽의 보고, "빌드됨", 남아 있던 화면은 확인으로 치지 않는다. 확인이 실패하면 확인 방법부터 의심한다.

## 보는 축과 지적

| 축 | 본다 |
|---|---|
| 요구 대조 | 요청·확정 결정·완료 기준을 채웠나, 빠진 것과 잘못 읽은 것 |
| 기준 | 프로젝트 규칙 문서와 검수 기준 문서, 작업에 쓴 스킬의 바로 할 일·완료 기준, 기존 관례, 분야 기준(보안·데이터·접근성·문서 형식) |
| 덜 짓기 | 요청 밖 추가, 쓰이지 않는 일반화·추상화·설정. 입력 검증·데이터 손실 방지·보안·접근성·요청한 것은 줄일 대상에서 뺀다 |

- 지적마다 위치(파일:줄, 쪽, 칸), 근거 인용, 등급(높음·중간·낮음)을 달고 높음부터 적는다. 근거를 대지 못한 취향, "나라면 다르게", 검사 도구가 이미 잡는 것은 지적으로 내지 않는다.
- 지적 0건도 정상 결과다. 그때는 본 범위와 시도한 반례를 적는다.

## 흐름

```
검수(끝에 한 번, 지적을 모아 한 번에)
 ├ 지적 없음 → 끝
 └ 지적 있음 → 만든 쪽이 한 번에 고침(높음·중간은 고침, 낮음은 고치거나 까닭)
               → 같은 검수자가 그 지적만 다시 봄: 해소 · 부분 · 미해소
                  ├ 모두 해소 → 끝
                  └ 부분·미해소 · 다시 볼 때 새로 나온 높음 · 만든 쪽이 근거로 받지 않은 지적
                       → 올림 한 장 → 한 단 위
```

- 다시 보기는 한 번이다. 바뀌지 않은 대상은 다시 검수에 보내지 않는다. 같은 지적이 되풀이되면 요구와 전제부터 다시 본다.
- 만든 쪽은 고치기 전에 지적의 인용 위치를 열어 맞는지 본다.
- 다시 보기는 처음 검수한 실행을 이어 부른다. 끊겼으면 같은 모델·노력의 새 실행에 직전 지적 목록과 고친 변경을 묶어 준다.
- 올림 꼴: `올림: 남은 것 · 양쪽 근거 · 추천 · 고르면 달라지는 것` 한 장. 위 흐름의 올림 조건에 들면 검수를 맡긴 쪽(한 단 위)으로 보낸다.
