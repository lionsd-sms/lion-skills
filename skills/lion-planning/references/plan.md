# 계획 쓰기

## 계획 꼴

```
[먼저 읽을 문단]
 사용자가 볼 결과 · 목적 · 정한 것 · 하지 않을 것 (전문 용어 없이)

[작업 단위]
 단위 1  이름
   할 일      : 무엇을 끝내나
   보게 될 것 : 끝나면 사용자가 보는 결과 한 줄(화면 상태, 출력 줄)
   완료 기준  : 누가 확인해도 같은 답이 나오는 문장 1~3개
   범위 밖    : 손대지 않을 이웃 일
   확인 방법  : 실행할 명령, 열어 볼 화면, 대조할 값
   읽을 자료  : 경로
   쓸 곳      : 경로
 단위 2 ...

[순서]
 1 ─┬─ 2 ─┐
    └─ 3 ─┴─ 4 ─ 검수(한 번)

[단위 사이 약속]
 넘길 파일 · 이름 · 형식 · 공통 낱말

[버린 안]
 견줘 본 방법과 버린 까닭 한 줄씩

[위험]
 어긋날 수 있는 것 · 그것이 드러날 단위
```

## 계획 조이기

단위를 쓰기 전에 세 가지를 본다.

- 이 일을 오래 한 사람이라면 어떤 원자료와 방법을 쓰고, 결과가 맞는지 무엇으로 확인하나. 그 방법을 단위와 확인 방법에 넣는다.
- 요청이 지나치게 세세하거나 비어 있지 않나. 목적에 쓰이지 않는 제약은 빼자고 제안하고, 빈 곳 가운데 사용자 몫은 질문으로 남긴다.
- 만든 쪽 밖에서 결과를 확인하는 수단(실제 실행, 원자료 대조, 다른 사람의 판정)이 계획에 하나 이상 있나.

## 완료 기준

- 동작과 결과로 쓴다. 예: 「이름 칸에 '김'을 넣으면 '김철수'·'김영희' 두 줄이 나온다」.
- 막연한 바람(「빠르게」, 「편하게」)은 확인할 수 있는 기준으로 바꾼다. 예: 「빠르게」 → 「목록이 1초 안에 뜬다」. 사용자가 정하지 않은 수치는 「제안」으로 표시해 묻는다.
- 목표 수치가 없으면 지금 값을 재어 적고 「지금보다 나빠지지 않음」을 기준으로 둔다.
- 완료 기준이 지금은 거짓인지 단위를 시작하기 전에 확인한다. 이미 참이면 그 단위는 할 일이 없거나 기준이 흐리니 기준을 다시 쓴다.
- 확인 지점은 이미 있는 것 가운데 가장 바깥(화면, 명령 출력)을 고르고, 지점 수를 적게 둔다.
- 프로젝트 규칙 문서에 모든 변경에 거는 완료 기준이 있으면 단위마다 함께 건다.
- 곧 실행할 계획은 경로를 적는다. 며칠 뒤 실행할 계획은 동작·이름·형식으로 적는다.

## 계획을 둘 곳

- 여러 에이전트나 다음 세션이 읽을 일은 파일 하나로 둔다. 프로젝트 규칙 문서가 자리를 정해 두었으면 그곳에 둔다.
- 남은 단위가 있는 기존 계획 파일은 덮어쓰지 않는다. 같은 일을 다시 짜면 그 파일을 고치고, 다른 일이면 어디에 둘지 묻는다.
- 에이전트에게 넘기는 단위는 대화를 물려받지 않은 사람이 읽어도 끝낼 수 있게 확정 결정과 읽을 자료 경로를 함께 적는다.
- 계획 파일이 있으면 단위가 끝날 때마다 그 단위의 상태(끝남 · 확인 결과)를 계획 파일에 고쳐 쓴다.

## 실행 중에 계획을 바꿀 사실이 나올 때

알릴 때는 해당하는 것을 빠뜨리지 않는다: 무엇을 찾았나 · 왜 중요한가 · 선택 · 제안 · 사용자 결정이 필요한가 · 지금 무엇을 하나.

| 찾은 것 | 처리 |
|---|---|
| 이미 정한 결과를 완성하는 데 필요한 처리(저장 뒤 목록 갱신) | 처리하고 알린다 |
| 보이는 결과를 바꾸는 새 선택 | 멈추고 묻는다. 그 선택에 기대지 않는 단위는 계속한다 |
| 이번 범위 밖의 다른 일 | 끝 보고에 후보로 모은다 |

계획 파일이 있으면 바뀐 결정을 먼저 계획에 고쳐 쓴 뒤 이어간다. 같은 방향의 수정이 거듭 실패하면 덧대기를 멈추고 완성 모습과 전제를 다시 확인한다.
