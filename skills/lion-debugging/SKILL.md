# 디버깅과 성능 진단

이 버그에서 실패하는 확인 수단을 먼저 만들고, 그것으로 원인을 가른 뒤 원인 자리에서 고치고, 같은 수단과 같은 화면에서 사라졌는지 확인한다.

## 함께 여는 스킬

이 스킬을 열었으면 파일을 읽거나 고치기 전에, 아래 조건에 맞는 스킬을 Skill 도구로 연다(Codex 는 그 스킬의 SKILL.md 를 읽는다). 이미 열려 있으면 건너뛴다.

- 로그·출력을 읽거나 코드를 고치거나 속도를 잴 때: `lion-dev-checks`

## 바로 할 일

오류 문구의 뜻이나 짐작 가는 원인만 묻는 질문에는 재현을 돌리지 않고 아는 것과 확인할 방법으로 답한다. 원인이 한 자리로 확인되는 작은 고장은 실패 확인 → 고침 → 같은 확인 통과로 끝낸다. 원인이 바로 보이지 않으면 아래 차례를 밟는다.

1. 보고를 정리한다: 증상 · 발생 조건 · 기대 결과 · 마지막 정상 상태 · 앱 판과 실행 환경 · 오류 문구 · 첨부. 받은 첨부는 모두 열어 본다.
2. 재현 수단을 만든다: 사용자가 말한 그 증상에서 실패하고 고치면 통과하는 명령 하나(실패 시험, 요청 스크립트, 고정 입력 실행, 화면 자동 조작). 한 번 돌려 실패를 본 것이어야 한다. 화면 증상은 실제 화면에서 따로 두 번 재현한다. 재현 수단 없이 가설 단계로 가지 않는다.
3. 재현을 줄인다: 입력·호출·설정·단계를 하나씩 빼고 다시 돌려 남은 요소가 모두 실패에 필요할 때까지.
4. 가설 3~5개를 세우고 "X가 원인이면 Y를 바꾸면 사라진다" 꼴의 예측을 붙인다. 한 번에 변수 하나만 바꿔 가른다.
5. 원인 자리에서 고친다: 증상이 드러난 곳에서 "왜"를 거슬러 처음 잘못된 결정까지 간다. 넣는 줄마다 실행 증거가 받친다. 증거가 반박한 가설로 넣은 변경은 되돌린다.
6. 확인하고 정리한다: 줄이기 전 원래 장면으로 재현 수단을 다시 돌려 통과를 보고, 맞는 시험 자리가 있으면 회귀 시험 하나를 남기고, 임시 계측과 시험물을 지운다. 커밋을 맡았으면 커밋 본문에 확인된 원인과 재현 명령을 적는다.

- 같은 전제를 깐 고침 두 개가 같은 확인에서 실패하면, 다음 고침 전에 그 전제를 한 문장으로 적고 직접 시험한다.
- 시험·빌드가 깨지면 그 자리에서 증거를 남기고 원인을 찾은 뒤 다음 일로 간다. 디버깅 변경에는 관계없는 변경을 섞지 않는다.
- 느림은 같은 조건에서 재어 기준을 잡고, 고침 하나마다 같은 방법으로 다시 잰다.
- 시험을 통과시키려고 기대값을 낮추거나, 시험을 지우거나 건너뛰거나, 검사를 끄지 않는다.
- 재시작 뒤에만 나는 실패는 남는 상태(설정 파일·캐시·잠금 파일)부터 본다.
- 고침을 줄일 때 줄이지 않는 것: 신뢰 경계의 입력 검증, 데이터 손실을 막는 오류 처리, 보안, 접근성, 실제 장비 보정, 사용자가 요청한 것.
