# 재현

재현 수단을 만들고, 화면 증상을 실제 화면에서 재현하고, 고친 뒤 같은 경로로 확인할 때 쓴다.

## 1. 재현 수단 만드는 차례

닿는 것 가운데 앞의 것부터 쓴다.

1. 버그 경로에 닿는 자리의 실패 시험(단위·통합·전체 흐름)
2. 띄운 개발 서버에 보내는 요청 스크립트
3. 고정 입력으로 명령줄을 돌려 알려진 정상 출력과 견주기
4. 화면을 자동으로 조작해 화면 요소·콘솔·네트워크를 단언하는 스크립트(브라우저·웹뷰는 브라우저 자동화 도구, 데스크톱 앱은 그 플랫폼의 화면 자동화)
5. 실제 요청·입력 자료·사건 기록을 파일로 떠서 그 코드 경로에 다시 흘려 넣기
6. 의존을 모의로 바꾼 최소 실행 틀에서 버그 경로를 함수 호출 하나로 부르기
7. "가끔 틀린 결과"면 무작위 입력 수백~수천 개를 돌려 실패 모양 찾기
8. 두 상태(커밋·자료·판) 사이에 생긴 버그면 "그 상태로 띄우고 확인"을 자동화해 `git bisect run`에 물리기
9. 같은 입력을 옛 판과 새 판(또는 두 설정)에 넣어 출력 차이 보기
10. 사람이 눌러야만 하면 그 사람이 할 단계와 볼 것을 차례로 주고 결과를 받아 오는 반자동 절차

## 2. 재현 수단의 완료 기준

다음을 모두 갖춘 명령 하나(스크립트 경로·시험 호출·요청 한 줄)를 이름 대고, 한 번 돌린 출력을 보인다.

- 실제 버그 경로를 지나고 사용자가 말한 그 증상을 단언한다. "오류 없이 돈다"는 이 기준을 채우지 못한다.
- 돌릴 때마다 같은 판정을 낸다. 간헐 결함은 반복·병렬·부하·지연 주입으로 재현율을 다룰 수 있을 만큼 올리고 그 재현율로 대신한다.
- 몇 초 안에 끝난다.
- 사람 없이 돌린다. 사람이 끼면 1절 10번 꼴로 묶는다.

이 명령이 생기기 전에 코드를 읽으며 원인 이론을 세우고 있으면 멈추고 이 절로 돌아온다.

## 3. 재현 수단을 만들 수 없을 때

장비·외부 서비스가 없어 막히면, 증상을 그 장비 이름 없이 다시 말해(예: "바코드 스캐너 입력이 두 번 들어간다" → "짧은 간격으로 같은 키 입력이 두 번 온다") 지금 환경에서 그 조건을 만들어 시험하고, 결과에 `바꿔 시험함`과 바꾼 조건을 적는다.

그래도 못 만들면 멈추고 그렇게 말한다. 시도한 것을 적고 필요한 것을 묻는다: 재현되는 환경에 닿을 길, 비밀값을 가린 캡처(네트워크 기록·로그 묶음·덤프·시각이 찍힌 화면 녹화), 임시 운영 계측 허락. 서브로 일하면 같은 내용을 `올림:`으로 넘긴다.

## 4. 실제 화면 재현

웹·웹뷰·데스크톱·모바일 어느 화면이든 같다.

먼저 일곱 가지가 되는지 확인한다: 대상 앱과 시험 환경 띄우기, 해당 기능 화면으로 가기, 실제 조작(클릭·입력·키·스크롤·끌기·창 크기·이동), 상태를 바꾸지 않고 읽기, 화면 갈무리, 화면 녹화, 프로세스·세션·임시 자료 정리. 하나라도 빠지면 막힘으로 적고 빠진 것을 밝힌다. 스크린샷 한 장, 단위 시험, 상태를 직접 바꿔 만든 장면, 소스 읽기는 화면 재현으로 치지 않는다.

1. 맞는 앱·작업 공간·계정·자료·기능 상태인지 앱 안의 표시로 확인한다. 창 순서나 익숙한 제목만으로 정하지 않는다.
2. 정상 끝 상태와 깨진 끝 상태를 먼저 이름 붙인다.
3. 보고된 경로를 실제 조작으로 따라가 둘이 갈리는 지점까지 간다. 예상된 대화 상자·불러오는 중·준비 단계는 버그가 아니다.
4. 두 번째 시도가 따로 서도록 상태를 되돌리고 같은 경로를 다시 밟아 같은 깨진 상태를 본다.
5. 될 때마다 실제 상태 값(저장된 자료·화면 요소 값·로그 줄)으로 교차 확인한다.

상태 읽기는 관찰을 확인하는 데만 쓴다. 상태를 주입해 증상을 만들면 재현이 아니다. 정한 시도 횟수 안에 재현되지 않으면 "재현 못 함"으로, 환경이 모자라면 "막힘"으로 보고한다. 재현이 확인되지 않으면 고치지 않는다.

증상까지의 전체 경로 녹화, 깨진 끝 상태 갈무리, 정확한 단계와 관찰을 적은 짧은 메모를 임시 자리에 남긴다. 갈무리·녹화·로그·토큰은 소스 관리에 넣지 않는다. 그다음 증거만 보고 "이 증거가 깨진 상태를 눈으로 보여 주나"를 따로 묻는다. 아니거나 불확실하면 더 나은 증거를 뜨거나 재현 못 함으로 둔다.

## 5. 고친 뒤 화면 확인

- 고치기 전 증거를 그대로 둔다.
- 고친 판을 실제로 띄워 같은 경로를 두 번 밟고, 깨진 상태가 사라지고 기대 상태가 그 자리에 오는 것을 본다. 고치기 전과 같은 상태 값으로 교차 확인하고 갈무리·녹화를 남긴다.
- 컴파일, 단위 시험, 코드 검토, 그럴듯한 차이는 고친 뒤 증거로 치지 않는다. "판단 불가"나 다른 화면에서 본 결과는 통과가 아니다. 그렇게 적는다.
- 바뀐 동작 둘레(이웃 상태·입력·권한·플랫폼·실패 경로)를 짧게 돌린다. 회귀가 남으면 끝내지 않는다.

## 6. 이미 있는 고침 확인

열린 PR이나 병합된 커밋이 이 증상을 고친 것으로 보이면 새로 고치지 않고 그것을 검증한다. 말·상태 표시·가지 이름만으로는 고침이 있다고 보지 않는다.

1. 사용자 변경을 덮지 않게 별도 작업 사본(worktree 같은)을 쓴다. 기준 판, 고친 판, PR·커밋 주소, 두 실행이 공유하는 빌드·환경 입력을 적는다.
2. 기준 판(열린 PR은 그 기준 가지, 병합된 고침은 바로 앞 판)을 띄워 증상을 두 번 본다. 두 번 보지 못하면 기준선이 없으므로 고침이 통한다고 말하지 않는다.
3. 고친 판을 같은 환경·자료로 띄워 5절대로 확인한다.
