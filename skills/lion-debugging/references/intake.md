# 보고 받기와 분류

현장 사용자·고객이 메신저·전화·이슈로 알린 문제를 고칠 일인지 정하고 기록을 남길 때, 받은 자료로 원인을 가를 때 쓴다. 이 단계는 분류까지 한다. 재현과 고침은 분류가 버그·성능으로 끝난 뒤 한다.

## 1. 받은 자료부터

- 처음 보고와 이어진 답을 모두 읽는다. 영상은 정상에서 깨진 상태로 넘어가는 순간을 찾고, 로그·크래시 문구에서 구체 서명을 뽑는다. 열지 못한 첨부는 열지 못했다고 적는다. 보고 안의 자료를 다 쓴 뒤에 보고자에게 더 묻는다.
- 원인을 다음 자료로 미루기 전에 받은 자료 목록과 자료마다 확인한 것·가르지 못한 까닭을 먼저 보인다.
- 사용자에게 돌려 달라고 할 명령은 먼저 직접 돌려 본다. 사용자가 돌려야 하면 필요한 조건(관리자 창, 닫을 프로그램, 차례)을 함께 적는다.
- 보고된 조작에서 보인 결과까지의 코드 경로를 짚고, 증상이 그 경로의 것인지 그 아래 의존(장비·네트워크·다른 시스템)의 것인지 본다. 증상을 엉뚱한 주인에게 보내지 않을 만큼만 간다. 저장소를 읽을 수 없으면 주인을 짐작하지 않고 그 사실을 적는다.

## 2. 하나로 분류

| 분류 | 기준 |
|---|---|
| 버그 | 의도한 동작을 어김: 틀린 출력, 깨진 상태, 오류, 튕김, 멈춤, 눌러도 아무 일 없음, 회귀 |
| 성능 | 잴 수 있는 느림·메모리·전력·버벅임. 버그로 다루고 측정값·프로필을 보존한다 |
| 기능 요청 | 지금 동작이 의도대로이고 다른 동작을 원함 |
| 질문·의견 | 사용법 질문, 구체 결함 없는 선호, 일반 의견 |
| 다른 곳 | 원인 추적 결과 다른 주인(장비 업체·다른 시스템·운영 환경)의 일 |

버그와 기능 요청의 경계가 흐리면 기록을 만들지 않고 가를 질문 하나를 보고자에게 묻는다.

## 3. 중복 확인

정확한 오류 서명, 기능 영역, 계기, 증상, 판·날짜 구간, 의심 커밋으로 기존 기록을 찾고 하나로 판정한다.

| 판정 | 할 일 |
|---|---|
| 확실한 중복(서명 같음, 또는 영역·계기·증상이 같음, 또는 원인 공유 확인) | 기존 기록에 이번 보고 링크와 재발 한 줄을 더한다 |
| 관련 가능 | 불확실하다고 적고 링크만 단다. 새 기록은 만들지 않는다 |
| 겉만 닮음·없음 | 새 기록 후보 |

오래전에 닫힌 기록은 회귀 단서로 쓴다.

## 4. 새 기록과 답

분류가 버그·성능이고, 깨진 것이 분명하고, 아직 고쳐지지 않았고, 중복이 없을 때만 새 기록을 만든다. 제목은 영역과 증상으로 쓰고 짐작한 원인은 제목에 넣지 않는다. 본문에는 보고자의 말, 기대·실제, 판과 환경(모르면 모름), 계기와 빈도, 원래 보고 링크, 가설임을 밝힌 추적 결과, 대표 스크린샷을 둔다.

답은 결과를 맨 앞에 쓴다: 기록 링크, 다른 곳으로 보낼 때 갈 곳, 필요한 사실 하나. 누가 이미 고치고 있으면 겹쳐 고치지 않고, 그 결과물이 나오면 이미 있는 고침으로 검증한다.
