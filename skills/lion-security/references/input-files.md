# 입력 경계와 파일 경로

## 경계 규칙

경계는 값을 누가 썼는지로 가른다. HTTP 요청 · 폼 · 업로드 · 웹훅 · 외부 API · 큐 · AI 모델 출력에 더해, 다른 프로세스의 명령줄 · 환경값, 공유 폴더의 파일 이름, 작업 입력에 담긴 경로도 운영체제가 건넸다는 이유로 내부 값이 되지 않는다.

경계마다 여섯 질문을 한 줄씩 답한다: 사칭할 수 있나, 변조할 수 있나, 했던 일을 부인할 수 있나(감사 기록), 새는 자료가 있나, 과부하로 멈출 수 있나(입력 크기 · 횟수 · 시간 상한), 권한을 넘을 수 있나. 답이 비는 곳이 점검의 첫 대상이다. 위협 모델을 문서로 남기라는 요청이 없으면 점검 보고에 경계 목록과 판정만 담는다.

## 받은 경로를 지우거나 옮기기 전

앱 코드든 지금 하는 작업이든, 설정 · 명령 인자 · 다른 프로세스 · 작업 자료에서 받은 경로는 모양이 맞아도 권한의 증거가 아니다. 지우거나 옮기거나 덮어쓰기 전에 넷을 모두 확인한다.

1. 링크(Windows 정션 · 심볼릭 링크)를 푼 실제 절대 경로가 허용 루트 아래에 있다. 재해석 지점을 따라 들어가 지우지 않는다.
2. 그 경로가 루트보다 한 단계 이상 아래에 있다.
3. 대상이 우리 것이라는 증거(소유 표지 · 생성 기록)를 작업 전에 읽었다. 폴더 안에 둔 소유 표지는 앱이 따로 가진 기록과 맞을 때만 근거로 쓴다.
4. 경로 값의 신뢰를 그 값을 쓴 주체로 갈랐다.

하나라도 어긋나면 거절한 대상을 기록하고 멈춘다. 더 넓은 기본 경로로 바꿔 진행하지 않는다. 실제 반영 · 복구 확인 없이 부분 실패를 성공으로 보고하지 않는다.

## 길이 · 정수 · 원시 메모리

Rust `unsafe`, C# `unsafe` · P/Invoke, Python `ctypes`, Dart `dart:ffi`, JS `Buffer.allocUnsafe` · WebAssembly 메모리, C/C++ 의 배열 · 포인터는 같은 경계다. 버퍼 문제는 길이 값이 어디서 왔고 어디서 검증됐는가로 판정한다.

1. 길이의 출처를 찾는다: 패킷 · 파일 헤더, 사용자 입력, 파싱 결과, 곱셈으로 계산한 크기.
2. 출처와 소비 사이의 상한 · 하한 · 정수 범위 검사를 찾는다. 검사가 소비와 같은 함수에 있는지, "호출자가 검사했을 것" 인지 적는다.
3. 소비 지점(복사 · 인덱스 · 할당 · 포맷 · 재귀 깊이)에서 검사한 길이와 실제로 쓰는 길이가 같은 변수인지 본다.
4. 좁히는 정수 변환, 부호 있는 값의 음수, 곱셈 · 덧셈의 넘침을 본다. Rust release 에서 `+` 는 조용히 감긴다.

검색은 3의 위험 호출만 찾는다. 1 · 2 · 4는 호출 경로를 읽는다. 그 언어에 이 경계가 없으면(Rust 에 `unsafe` 0건 따위) 실제 코드 경계를 열어 본 근거와 함께 `N/A` 로 닫는다. 검색 0건만으로 닫지 않는다. 확인하지 않은 경계는 `NOT VERIFIED` 다.
