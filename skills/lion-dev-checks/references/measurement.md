# 측정 숫자

속도·지연·처리량·자원 사용처럼 잰 숫자를 보고하거나, 그 숫자로 무엇을 고르기 전에 쓴다. 답은 코드를 읽은 추측에서 받지 않고 실행 근거에서 받는다.

## 재기 전

- 보고할 문장을 먼저 적는다. 예: "6만 행 자료에서 내보내기가 p50 기준 30% 빨라짐". 아래 질문은 이 문장을 시험한다.
- 측정 스크립트를 읽고 무엇을 재고, 세고, 빼는지 적는다.
- 기기 부하와 코어 수를 본다. 바쁜 기기를 비울 수 없으면 양쪽을 번갈아 돌려 같은 잡음을 받게 하고 보고에 적는다.

## 일곱 질문

1. 왜 두 배가 아닌가: 결과를 묶는 자원이나 코드 경로(코어, 잠금, 디스크, 네트워크, 부하 생성기)를 프로파일이나 실행 중 시스템 계수로 찾아 코드 위치에 잇는다. 프로파일은 보고하지 않는 실행에서 돌린다. 숫자가 움직이지 않은 변경도 제한 요인을 찾은 뒤에 쓸모를 판정한다.
2. 양쪽을 운영처럼 맞췄나: 릴리스 빌드, 운영 설정·환경 변수, 묶음·트랜잭션 설정, 연결 풀, 운영과 같은 캐시 상태, 같은 판과 자료로 돌린다. 한쪽만 기본값이면 설정을 견준 것이다. 제한 요인이 설정(행마다 커밋, 디버그 빌드, 빠진 색인)이면 맞춘 뒤 다시 잰다. 맞출 수 없으면 그 실행으로 승자를 고르지 않는다.
3. 물리 한계를 넘었나: 초당 바이트를 디스크·네트워크 대역폭과, 초당 연산 수 × 연산 비용을 코어 수와, 줄어든 시간을 바뀐 부분이 차지하던 시간과 견준다. 전체의 10%를 차지하는 부분을 없애도 전체는 약 11%까지만 빨라진다. 한계를 넘은 결과는 캐시·빈 동작·결함을 잰 것이다.
4. 오류가 났나: 실패와 비정상 응답 수를 세고, 출력이 있는지와 함께 맞는지 본다. 거절은 빠르고 시간 초과·재시도는 느리다. 스크립트가 오류를 세지 않으면 세게 고친다.
5. 되풀이되나: 양쪽을 A, B, A, B 순으로 번갈아 5번 이상 돌려 중앙값과 범위를 낸다. 실행 사이 흔들림보다 작은 차이는 차이 없음이다. 아슬아슬하면 순위합 검정이나 측정 도구의 통계를 쓴다.
6. 전체에서 중요한가: 작은 부분의 결과 옆에 사용자가 기다리는 전체 경로를 실제 자료 크기·동시성으로 재고, 작은 결과를 전체에서 차지하는 몫으로 적는다.
7. 일이 실제로 일어났나: 잰 구간 안에서 요청이 서버에 닿았는지, 행이 써졌는지, 바이트를 읽었는지, 코드가 결과를 썼는지 확인한다. 아무도 돌리지 않은 지연 실행, 기다리지 않은 비동기, 버려진 결과, 시간 초과는 일어나지 않은 일의 숫자를 만든다.

사용자가 대략만 원하면 한 번 돌리고 4·7번을 확인한 뒤 한 번 돌린 숫자라고 적는다. 나머지는 그 실행이 이상해 보일 때만 본다. 여러 선택지 가운데 고르는 일은 대략으로 하지 않는다.

## 보고

- 판정을 먼저 쓴다: 빨라짐 · 느려짐 · 차이 없음 · 결론 못 냄.
- 숫자와 단위, 실행 횟수, 범위, 제한 요인, 잰 자리(기기·빌드 종류·자료 크기)를 함께 쓴다. 예: "p50 41ms → 33ms, 양쪽 7회 중앙값, 바꾼 뒤 범위 32~35ms, 한 코어의 JSON 해석이 제한 요인, 사무실 PC·릴리스 빌드·6만 행".
- 차이를 주장하는데 제한 요인을 대지 못하거나, 한쪽을 맞추지 못했거나, 4·7번을 확인하지 못했으면 결론 못 냄으로 두고 빈 곳을 적는다.
- 실행 기록·범위·제한 요인 근거는 메모 파일에 함께 남긴다.

## 숫자를 목표로 되풀이 개선

지표 하나를 목표까지 여러 번 고쳐 올리는 일에 쓴다. 한 번 고치는 일은 위 질문과 아래 절을 쓴다.

1. 사용자 불만을 재현하는 작업량(자료 크기·이력·상태·동시성)을 고른다. 재현하는 경우가 없으면 재현부터 만든다.
2. 지표 하나, 나아지는 방향, 확인할 수 있는 멈춤 조건을 정한다. 멈춤 조건은 목표와 최소 시도 횟수를 짝짓는다(예: "기준보다 50% 이상, 시도 10번 이상"). 사용자가 준 숫자가 있으면 그것을 쓰고, 없으면 사용자와 정한다.
3. 측정 장치를 만들고, 쉬운 경우와 재현 경우를 실제로 가르는지 본 뒤, 일곱 질문으로 점검하고 고정한다. 장치는 오류 수와 한 일의 양을 함께 찍는다. 기준 지표와 지켜야 할 시험의 통과를 먼저 기록한다.
4. 한 번에 가설 하나: 구체적 원리를 댄 가설 → 변경 → 고정한 장치로 전후 측정과 지켜야 할 시험. 잡음을 넘어 나아지고 시험이 통과할 때만 남기고, 아니면 통째로 되돌린다. 시험하지 않은 변경을 쌓지 않는다.
5. 시도마다 한 줄을 기록한다: 가설 · 변경 · 전 · 후 · 차이 · 시험 · 남김/되돌림. 기록은 작업 트리 밖에 두고 시도 전에 읽는다.
6. 정체되면 가설 갈래를 바꾸거나, 아깝게 놓친 것들을 합치거나, 원본을 다시 읽는다. 정확성과 단순함을 숫자보다 앞에 둔다. 동작을 깨는 개선은 되돌리고, 숫자를 지키는 단순화는 남긴다.
7. 멈춤 조건을 채우거나 남은 가설이 모두 잡음 수준의 효과만 기대될 때 멈춘다. 멈춤 조건을 느슨하게 고치지 않는다. 막히면 `올림:` 으로 넘긴다.

보고: 지표와 목표, 기준 → 최종(차이 %), 시도 수(남김·되돌림), 남긴 수정 한 줄씩, 기록 파일 위치, 더 하면 해 볼 가설.

## 성능 고침 하나를 남길지

- 고침 하나도 위 4번의 남김·되돌림 기준과 5번의 기록 꼴을 따른다. 기록은 그 일의 기록 자리에 둔다.
- 효과의 근거는 이번에 잰 지표 값이다. 종합 점수와 일반적인 절감 수치는 근거로 쓰지 않는다.
- 캐시로 빨라진 고침은 원본이 바뀐 뒤 낡은 값이 보이는 경우를 돌려 본 뒤에 남긴다. 틀리면 안 되는 값(재고 수량·금액·권한)은 캐시하지 않는다.
