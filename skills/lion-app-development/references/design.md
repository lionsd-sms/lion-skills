# 설계

인터페이스·자료 모양·모듈 경계를 새로 정하거나 바꿀 때 이 파일을 쓴다. 한 곳을 고치는 작은 수정은 고치는 방식과 덜 짓기로 끝낸다.

## 1. 쓰는 쪽부터

- 요청이 기존 코드에 대한 사실을 깔고 있으면(예: "저장할 때 이미 중복을 막으니까") 설계 전에 그 사실을 가설로 두고, 그 코드와 그것을 쓰는 곳을 세어 확인한다. 사실과 다르면 설계 전에 알린다.
- 고치기 전에 닿는 하위 체계를 읽어 지금 설계를 설명할 수 있게 한다: 무엇이 무엇을 부르고, 상태는 누가 갖고, 자료가 어디로 가나.
- 쓰는 쪽 사용법(호출 예 두세 개: 무엇을 가져와 무엇을 부르고 무엇을 받나)을 먼저 쓰고 타입·함수 꼴을 거기서 끌어낸다. 둘이 어긋나면 꼴을 사용법에 맞춘다.
- 자료 모양을 논리보다 먼저 정한다. 핵심 타입을 먼저 두고 자주 쓰는 읽기·쓰기 경로에 맞는 구조를 고른다.
- 새 요구는 처음부터 있던 전제처럼 설계하고 기존 설계에 덧대지 않는다. 바뀐 전제를 타입·문서·예시·까닭 설명까지 옮긴다. 전체를 설계한 뒤 조각으로 나눠 넣는다.

## 2. 후보 둘 이상

선례가 없는 구조·인터페이스 결정은 모양이 다른 후보를 둘 이상 그려 견준다. 한 모양 안의 작은 변형은 다른 후보로 치지 않는다.

- 견줄 축: 공개면의 크기와 그 뒤에 숨기는 일의 양, 바뀔 때 고칠 곳이 한곳에 모이는가, 시험이 공개면만으로 되는가. 작은 공개면 뒤에 많은 일을 숨긴 쪽을 고른다.
- 한 파일만 열어 본 다음 작업자가 가장 가까운 예를 베껴도 저장소 전체에서 맞는 쪽을 고른다.
- 구조·저장·호환 대안은 지킬 동작과 제약을 먼저 고정한 뒤 각 안의 실패 방식·전환 순서·되돌릴 조건·확인 근거로 견준다. 찬성 수보다 남은 반론과 실제 반증을 본다.
- 같은 결과의 내부 선택은 근거로 정하고, 보이는 결과·사용 흐름·정책이 갈리는 선택만 사용자에게 묻는다.
- 고른 안의 까닭을 짧게 남긴다: 쓰는 쪽 사용 예, 고른 꼴, 받아들인 맞바꿈, 버린 후보와 까닭 한 줄. 남길 자리는 프로젝트 규칙 문서를 따른다.

## 3. 설계 경고

후보마다 아래가 보이면 고치거나 버린다.

| 경고 | 모습 | 고치는 쪽 |
|---|---|---|
| 얕은 모듈 | 공개면이 안의 일만큼 크다. 한 일을 하려고 여러 메서드를 차례로 불러야 한다 | 공개면을 줄이고 일을 안으로 모은다 |
| 정보 새어 나감 | 같은 내부 결정(표현·정책·프로토콜 세부)이 여러 모듈에 있다. 전송·저장 타입을 공개면으로 내보낸다 | 경계에서 업무 타입으로 바꾸고 세부는 안에 둔다 |
| 실행 순서로 쪼갬 | 읽기·검사·변환·저장 단계마다 모듈이 있고 같은 규칙이 되풀이된다 | 가진 지식과 주인으로 묶는다 |
| 전달만 하는 층 | 같은 인자를 같은 꼴로 넘기기만 한다 | 지우거나 일을 끝낼 수 있는 쪽으로 옮긴다 |
| 나뉜 주인 | 두 모듈 이상이 같은 상태를 쓰거나 사본을 갖는다 | 주인을 하나로 두고 나머지는 읽거나 주인에게 맡긴다 |
| 같은 일의 두 길 | 같은 일을 하는 방법이 둘 이상이다 | 하나만 남기고 호출처를 옮긴 뒤 나머지를 지운다 |
| 안이 드러남 | 밖에서 내부 파일을 가져다 쓸 수 있다 | 밖에서 가져오면 빌드가 실패하게 막는다 |
| 손으로 맞추는 목록 | 같은 항목 목록이 여러 곳에 있다 | 하나에서 끌어내거나 어긋나면 빌드가 실패하게 한다 |

- 삭제 시험: 모듈을 지운다고 생각해 복잡도가 사라지면 전달만 하는 껍데기다. 호출처 여러 곳에 다시 나타나면 제 몫을 한다.
- 교체 지점(접점)은 실제로 갈아 끼울 것이 둘(예: 실제 연결과 시험용) 있을 때만 둔다. 하나뿐이면 간접층이다.

## 4. 모델과 경계

- 업무는 상태 기계, 판별 유니온, 표·등록부, 타입 모델에 담아 잘못된 상태를 만들 수 없게 하고, 참거짓 값·단계 이름·수명 점검으로 흩뜨리지 않는다. 신호: 새 기능이 기존 if/else 사슬에 갈래 하나를 더하거나, 늘 첫째와 맞춰야 하는 둘째 참거짓 값이 생긴다. 지금 꼴이 분명하고 국소적이며 자랄 일이 없으면 평범한 코드로 둔다. 분기·중복 규칙·잘못된 상태를 지우지 못하는 간접층은 넣지 않는다.
- 검증·형 좁히기·오류 처리는 시스템 경계(명령 인자, 설정 파일, 외부 API, 네트워크, 파일·DB 읽기)에서 한다. 경계에서 날 자료를 업무 타입으로 바꾸고 안에서는 그 타입을 믿어 다시 검사하지 않는다. 판정: 이 자료가 지금 경계를 넘나. 아니면 그 검증은 지운다.
- 업무 논리는 프레임워크에 기대지 않는 순수 함수에 두고, 바깥 껍데기는 그것을 부르기만 한다.
- 뜻이 다른 원시값(사용자 ID와 주문 ID 따위)은 서로 바꿔 넣을 수 없는 타입으로 나누고 만들 때 한 번 검증한다. 스키마·DB 전환·토큰 파일처럼 모양의 주인이 있으면 타입을 거기서 끌어낸다.
- 의존은 안에서 만들지 않고 받는다. 결과를 돌려주는 함수를 상태를 바꾸는 함수보다 먼저 고른다.
- 상태를 다른 실행자와 나누기 전에 다른 쪽이 동시에 바꾸면 어떻게 되는지 묻고, 답이 「아무 일 없음」 이 아니면 떼어 놓는다.

## 5. 구현 중 설계 버리기

고른 꼴이 구현의 계약이다. 꼴에 없던 인자가 필요해지면 꼴이 틀렸는지, 요구를 놓쳤는지, 구현이 넘치는지부터 가린다.
아래가 되풀이되면 덧대기를 멈추고 지금까지 만든 것을 다시 읽은 뒤, 새 전제를 처음부터 있던 것처럼 다시 그린다. 새 꼴은 옛 꼴보다 작게 시작한다.

- 서로 무관한 곳에 같은 모양의 우회가 거듭 생긴다.
- 서로 무관한 경계 사례마다 특수 분기가 필요하다.
- 컴파일하려고 any·형 변환·늘 채워지는 선택 칸이 필요하다.
- 공유하지 않는다던 상태에 잠금이 필요해진다.
- 호출하는 쪽이 추상화의 내부 규칙을 알아야 쓸 수 있다.

경계 사례 몇 개로는 설계를 버리지 않는다. 자료의 복잡함과 설계의 복잡함을 가른다.
