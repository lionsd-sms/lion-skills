# 화면 방향·구성·문구

화면 원칙을 고른 앱(프로젝트 규칙이 「화면은 값과 동작만」을 정한 앱)은 화면 원칙과 문구 꼴이 이 파일보다 앞선다. 이 파일에서 도움말·안내 문장을 권하는 줄은 그 밖의 프로젝트에 쓴다.

## 1. 기존 화면을 다루는 수준

실제 화면·코드·사용자 흐름에서 만족·불만, 제품 계약, 플랫폼 제약을 확인하고 수준을 정한다. 사용자 요청이나 확인한 프로젝트 근거가 정한 방향을 다시 쓰고, 불만이 드러나면 유지 가정을 다시 판단한다.

| 수준 | 하는 일 | 기존 화면의 지위 |
|---|---|---|
| `PRESERVE` | 방향을 유지하며 기능·결함 수정 | 강한 참고값. 기존 카드 언어가 제품 패턴이면 유지 |
| `TUNE` | 구조를 유지하며 시각·상호작용 정돈 | 구조 보존, 표현 변경. 불필요한 테두리·그림자·모서리를 줄임 |
| `IMPROVE` | 불편·복잡·발견성까지 개선 | 관찰 근거. 정보구조와 훑는 속도로 표면을 재편 |
| `REDESIGN` | 기능·자료 계약을 지키며 재설계 | 시각·배치의 기준으로 쓰지 않음. 업무와 정보 위계부터 |

결과를 크게 바꾸는 미정 방향은 현재 화면·사용자 선택·프로젝트 근거로 좁혀 추천안과 함께 묻는다. 이미 정했거나 맡긴 방향은 다시 묻지 않는다.

방향이 정해지지 않았으면 핵심 업무와 정보 우선순위를 먼저 드러내고, 여백·글자·묶음으로 위계를 만들며, 대상 플랫폼의 익숙한 이동·제어·입력을 쓰고, 브랜드 근거가 없으면 중립색·시스템 글꼴에서 시작한다.

## 2. 표면 구성

카드·패널·상자는 기본 배치 부품이 아니다. 내용이 독립된 표면이라는 뜻을 전할 때만 쓴다. 새 구역은 가장 약한 구분 수단부터 보고 필요한 뜻이 생기는 단계까지만 올라간다.

```text
정렬·여백 → 글자 위계 → 구분선·묶음 → 옅은 배경 영역 → 패널 → 테두리·그림자 있는 카드
```

- 카드가 맞는 곳: 반복되는 개체(상품·프로젝트·문서), 따로 선택·열기·끌기·순서 바꾸기를 하는 항목, 서로 견주는 같은 급의 항목(요금제·옵션), 표면 차이가 상호작용 뜻을 갖는 패널. 많은 자료를 빠르게 훑는 업무 화면에서는 독립 개체도 행·표·목록이 낫다.
- 카드를 기본값으로 쓰지 않는 곳: 쪽 제목·설명, 검색·필터·정렬 도구줄, 폼의 모든 칸 묶음, 설정의 하위 절, 표·목록을 감싼 장식 상자, 이어진 절을 하나씩 감싼 상자, 카드 안의 카드.
- 경계가 필요한 까닭을 독립 개체·상호작용 범위·높이·선택·스크롤 가둠 가운데 하나로 대지 못하면 상자를 걷는다.
- 카드 과다 신호: 거의 모든 절이 `배경 + 테두리 + 모서리 + 안쪽 여백` 조합을 가짐, 카드 안에 카드와 테두리 블록이 되풀이됨, 위계 단계마다 테두리나 그림자를 더함, 배지·칩·배경 색을 정보 구분의 기본 수단으로 씀, 상황판이라는 까닭만으로 모든 값을 KPI 카드 격자로 만듦, 상자를 걷으면 정보구조가 사라질 만큼 글자·간격 위계가 약함.
- 중첩 표면은 경계마다 뜻이 달라야 한다. 시각 구분만 필요하면 안쪽 카드를 제목·간격·구분선으로 평탄화한다.

| 목적 | 카드 대신 먼저 볼 것 |
|---|---|
| 절 구분 | 여백, 제목, 구분선 |
| 설정 묶음 | 절 제목 + 행 |
| 검색·필터 | 도구줄 |
| 많은 자료 | 표, 목록, 촘촘한 행 |
| 목록과 상세 | 나뉜 창 |
| 같은 화면의 범주 | 탭 |
| 폼 묶음 | 칸 묶음 + 제목·legend |

실제 화면에서 중첩 표면을 하나씩 걷었을 때 뜻이 실제로 사라지는지, 카드 안쪽 여백 때문에 자료 비교와 작은 화면의 내용 폭이 줄지 않는지 확인한다.

## 3. 화면 문구

라벨과 실행 중 값을 나눈다. 라벨·상태 낱말은 고정하고 값은 칸·행·표 칸·목록 항목으로 보인다.

- 상태는 제한된 낱말로 쓴다(`연결됨 / 연결 안 됨 / 사용 안 함 / 오류`). 성공이 화면 상태로 분명하면 그 상태를 주 피드백으로 쓴다.
- 조작 요소와 구조가 목적을 보여 주면 설명문을 지운다: 선택 칸 아래 「이 설정에서는 연결할 장비를 선택할 수 있습니다」, 단추 위에서 단추 이름을 다시 풀어 쓴 문장, 현재 값을 「~은 ~입니다」로 다시 쓴 문장.
- 도움말은 라벨만으로 알 수 없는 제약·결과·예외가 있을 때만 둔다. 경고는 실제 결과가 있을 때만 쓴다.
- 오류는 실패 대상·결과와 사용자가 고칠 수 있는 내용을 알리고, 다음 행동은 누를 수 있는 조작으로 준다. 내부 스택과 비밀값은 화면에 두지 않고 허용된 로그에 남긴다.

화면 원칙을 고른 앱의 확인 문구 예: `장비 연결 해제 · 측정 중 [해제] [취소]`

점검: 이 문장 없이 조작 요소·라벨·값으로 뜻이 전해지나, 같은 상태를 화면마다 다르게 쓰나, `주의`·`안내`·`참고`를 정보 없이 꾸밈으로 썼나.

## 4. AI가 만든 티

방향이 정해지지 않은 화면을 새로 만들 때 모델이 기본으로 고르는 모양을 피한다: 프로젝트와 무관한 보라·남색 위주 색, 장식용 그라데이션, 모든 모서리를 크게 둥글림, 내용과 무관한 큰 첫 화면 띠, 자리 채우기 글, 어디나 넓은 여백, 정보 우선순위를 무시한 같은 크기 카드 격자, 겹겹 그림자. 프로젝트의 색 토큰·간격 단계·모서리 값과 실제 길이의 내용으로 배치한다.
방향이 열려 있으면 비슷한 업무 화면 두세 개를 보고 위계·밀도·탐색·조작·상태의 결정을 짧게 적은 뒤 프로젝트 부품으로 다시 짓는다. 남의 상표·문구·이미지·배치를 그대로 옮기지 않는다.

## 5. 디자인 방향 불만

- 이미 보인 앱 화면에 사용자가 "디자인이 별로다", "마음에 안 든다", "다른 느낌으로"처럼 방향 전체에 불만을 보이면, 다음 안을 만들기 전에 시안을 여러 개 견줄지 묻는다. 불만만으로는 원하는 방향을 알 수 없고, 한 안씩 짐작해 고치면 같은 왕복이 되풀이된다. 사용자가 개수를 말하지 않으면 시안은 두 개로 한다.
- "제목 글씨만 키워줘"처럼 고칠 부분을 짚었으면 그 부분을 바로 고친다. 하나만 달라고 했으면 여러 안을 제안할지 다시 묻지 않는다. 질문할 수 없는 무인 실행에서는 한 안을 만들고 다른 방향도 가능하다고 밝힌다.
- 이 기준은 앱 화면의 시각 방향에만 쓴다. 기능·자료·동작 계약에 대한 불만과 앱 밖 문서·라벨·이미지 산출물에는 쓰지 않는다.
