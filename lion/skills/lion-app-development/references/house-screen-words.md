# 화면 원칙과 문구 꼴

프로젝트 규칙 문서의 「폴더 틀」 절 `틀:` 줄이 이 원칙을 담은 틀을 가리키거나 「화면·문구 원칙」 절이 「화면은 값과 동작만」을 정한 앱에 쓴다. 이 스킬의 다른 문서에서 「화면 원칙을 고른 앱」은 이 앱을 뜻한다. 그 밖의 프로젝트는 그 프로젝트의 규칙과 화면 방향·구성·문구 지침을 쓴다. 1~5절은 화면, 6~9절은 문구 꼴이다.

## 1. 네 줄

- 내부 복잡성은 개발자와 AI가 감당한다. 이를 프로그램 운용자에게 절차나 판단 부담으로 전가하지 않는다.
- 인터페이스는 단순하고 직관적으로 유지한다. 불필요한 정보, 선택지, 버튼, 상태를 동시에 노출하지 않고 사용자가 현재 해야 할 일을 즉시 알 수 있게 한다. 시각적 인지 부하를 최소화한다.
- 기능은 필요할 때만 드러낸다. 기능 수가 늘어도 화면에 보이는 기능 수를 함께 늘리지 않는다. 현재 맥락에 필요한 기능만 우선 노출하고 나머지는 단계적으로 드러낸다. 기능 추가를 곧바로 버튼·메뉴·탭 추가로 해결하지 않는다.
- 화면은 값과 동작만 보인다. 까닭·안내·다음 확인은 툴팁·상세·실패 문구에도 두지 않고 실행 로그에 남긴다. 오류 문구는 `실패 대상 · 실패` 한 구로 끝낸다. 사용자가 직접 고쳐야 하는 입력 오류만 고칠 것을 한 구 더 보인다(예: `이메일 · 형식 틀림`).

## 2. 화면에 두지 않는 것

- **값과 동작만.** 화면 문구는 고정 라벨과 동적 값, 그리고 단추(동작)로 이룬다. 설명형 문장, 안내문, 까닭 문장은 화면 어디에도 두지 않는다. 툴팁에는 값(원래 시각 따위)이나 아이콘 단추의 이름만 둔다.
- **오류.** 원인·다음 행동 문장과 도움말 링크를 두지 않는다. 복구는 단추로 둔다.
- **빈 상태.** 아이콘·안내 문장을 두지 않는다.
- **입력 칸.** 칸 아래 도움 문장을 두지 않는다.
- **확인창.** 결과를 설명하는 문장을 두지 않는다. 값과 단추로 이룬다.
- **기능은 필요할 때만.** 지금 맥락에서 쓸 수 없는 기능은 까닭을 적은 비활성 자리로 남기지 않고 숨긴다.
- **진행 중 밀림.** 작업이 도는 동안 줄이 새로 생기거나 사라지거나 밀리지 않게 진행 표시와 결과의 자리를 처음부터 잡아 둔다.
- **여럿의 이름.** 같은 종류가 여럿이면 이름을 늘어놓지 않고 수로 보인다(예: `모니터 2대`).
- 프로그램이 근거로 정할 수 있는 값을 설정·선택 칸으로 사용자에게 넘기지 않는다.

## 3. 예외

예외는 사용자가 그 앱에만 따로 허락한 것뿐이고, 프로젝트 규칙 문서(또는 그 앱의 UI 문서)에 적힌 것만 그 앱 안에서 쓴다.
예: 어떤 앱의 첫 실행 안내 화면 한 문단. 스킬이 예외를 먼저 만들지 않는다. 설명 문장이 꼭 필요해 보이면 화면에 넣기 전에 그 앱의 예외로 둘지 사용자에게 묻는다.

## 4. 모양

탐색기·엑셀 같은 평평하고 빽빽한 업무 화면이다. 위계는 굵기·간격·가는 선으로 나누고 상자는 한 겹 이하로 쓴다.
카드 상자, 알약 모양, 이모지, 그라데이션을 쓰지 않는다.
색·밝기·글꼴과 다크 모드를 둘지는 앱마다 정해 그 앱의 UI 문서나 결정 기록에 적는다.

## 5. 일반 지침과의 관계

화면 방향·구성·문구 지침의 행 가운데 도움말·안내 문장을 권하는 것은 그 밖의 프로젝트에 쓴다. 화면 원칙을 고른 앱에서는 이 문서가 앞선다.
두 지침이 부딪치지 않는 행(접근성 이름, 키보드·초점, 대비, 실제 창 크기에서의 확인 따위)은 그대로 쓴다. 접근성 이름과 초점 이동은 이 문서의 규칙과 함께 늘 지킨다.

## 6. 화면 낱말

- **관습 업무 용어 명사구만 쓴다.** 업무 문서나 다른 업무 앱에서 이미 쓰는 말이다(접수 · 반영 예정 · 반려, 반영 · 미확인, 버전 · 업데이트, 저장 위치). 낱말을 새로 쓸 때마다 "업무 문서나 다른 업무 앱에서 이미 쓰는 말인가" 를 먼저 본다.
- **지어낸 말을 쓰지 않는다.** AI 가 편하게 지어낸 말(받음 · 다음판 · 안함 · 채움 · 비움 · 근거 · 새 판 · 판 · 건 폴더 · 받아쓰기 · 단어장 · 어느 쪽 따위. 화면에서 판은 버전이라고 쓴다)은 화면에도, 시안·명세에도 넣지 않는다. 표준 용어로 바꾼다.
- **기존 화면 이름을 유지한다.** 앱에 이미 있는 이름(단추·메뉴·묶음 제목)은 사용자가 바꾸라고 하기 전에는 그대로 둔다.
- **낱말 표는 앱마다 한 곳이다.** 그 앱의 UI 문서(폴더 틀이 정한 자리)의 낱말 표가 화면 낱말의 단일 출처다. 표에 없는 낱말이 필요하면 표에 먼저 더한다. 파일·폴더 이름과 JSON 키 같은 기계 계약은 표 밖이다.

## 7. 역할별 꼴

| 역할 | 꼴 |
|---|---|
| 단추·메뉴·라벨 | 관습 업무 용어 명사구(6절) |
| 상태 | `고정 라벨 · 동적 값`(예: `상태 · 연결됨`) |
| 오류·입력 검증 | `실패 대상 · 실패` 한 구로 끝낸다. 사용자가 직접 고쳐야 하는 입력 오류만 고칠 것을 한 구 더 보인다(예: `이메일 · 형식 틀림`). 원인과 다음 확인은 실행 로그(8절)에 남기고, 복구는 동작(다시 시도 따위)으로 둔다 |
| 경고·확인창 | 값과 단추(예: `장비 연결 해제 · 측정 중 [해제] [취소]`). 결과를 설명하는 문장을 두지 않는다 |
| 빈 상태 | `종류 · 없음` 한 줄과 필요하면 동작 하나 |
| 입력 칸 예시 | 칸 안의 예시 값(`예: 2026-09-28`)만 두고 칸 아래 도움 문장을 두지 않는다 |
| 도움말 | 화면에 두지 않는다. 그 앱의 규칙이 따로 허락한 예외만 둔다 |
| 매뉴얼·README·개발문서 | 일반 기준의 순서에 한국어 평서형(~다). 문서 머리·자리와 README 의 시작 방법은 프로젝트 규칙 문서의 폴더 틀을 따른다 |
| 사람이 읽는 CLI 출력 | `대상 · 상태: 까닭`(실행 로그 한 줄에서 시각을 뺀 꼴). 프로그램이 읽는 값은 그 계약을 따른다 |
| CHANGELOG·출시 기록 | 실제 사용자·운영 영향 중심, 존댓말(~합니다) |

## 8. 실행 로그

화면 원칙을 고른 앱은 실행 로그를 반드시 두고, 화면에서 뺀 까닭·안내·다음 확인을 로그에서 찾을 수 있게 한다.

- 자리: 프로젝트 규칙 문서의 폴더 틀을 따른다.
- 한 줄 꼴: `YYYY-MM-DD HH:MM:SS <대상> · <상태>: <까닭>`. 예: `2026-09-28 14:32:10 요청 · 실패: 공유 폴더에 닿지 않음`. 화면의 `실패 대상 · 실패` 와 같은 대상 낱말을 써서 화면에서 본 것을 로그에서 바로 찾게 한다.
- 입구: 단추·실행 파일·예약 작업 가운데 둘 이상이 한 로그에 쓰는 앱만 줄 앞에 `[<입구>]` 를 붙인다. 예: `[예약 백업] 2026-09-28 14:32:10 요청 · 실패: 공유 폴더에 닿지 않음`.
- 입구 이름은 실행이 시작되는 자리에서 붙여 연결 식별값과 함께 아래로 넘긴다.
- 아래쪽 코드에서 입구를 짐작해 채우지 않는다.
- 비밀값·불필요한 개인정보는 적지 않는다.

## 9. 표기

화면 원칙을 고른 앱의 글에는 다음 표기를 지킨다.

- **긴 줄표(U+2014)를 쓰지 않는다.** 삽입구는 쉼표나 괄호, 콜론으로 처리하거나 문장을 나눈다. 제목의 부제는 콜론, 적용 조건 단서는 괄호가 맞다. 가운뎃점(·), 화살표(→), 하이픈(-)은 그대로 쓴다.
- 인용 원문에 원래 있던 것, 외부에서 가져온 자료의 본문, 불변 기록으로 저장된 산출물은 예외다.
