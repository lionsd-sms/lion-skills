# 개발 문서와 문구

화면 원칙을 고른 앱은 화면 원칙과 문구 꼴이 이 파일보다 앞서고, 프로젝트 규칙 문서의 「화면·문구 원칙」 절이 있으면 그것이 먼저다.

## 1. 코드 주석

- 주석과 문서 문자열에는 지금 책임·입출력 계약·불변 조건·제약과 코드만으로 오해하기 쉬운 까닭(외부 제약·보안·순서와 동시성·임시 우회의 제거 조건)을 짧게 남긴다. 코드를 그대로 읽어 주는 설명은 쓰지 않는다.
- 날짜별 작업일지·작업자·수정자 메모·이번 수정·예전 구현·AI 와의 대화와 AI 가 한 일은 코드에 남기지 않고 기존 결정·기록·변경 이력 문서에 합친다. 날짜별 빈 보고서를 늘리지 않는다.
- 풀리지 않은 TODO·FIXME 는 지금 위험·제약이면 추적 대상으로 두고, 문서로 옮기면 유효한 연결을 남긴다. 해결하지 않고 지워서 끝난 것으로 만들지 않는다.
- 라이선스·저작권, 프라그마, 형 검사·검사기·컴파일러·생성기 지시, 외부 프로토콜 표식, 문서 생성에 쓰이는 공개 API 계약은 꼴이 주석이어도 옮기거나 지우지 않는다.
- 코드와 문서를 맞출 때 문서를 지금 결함에 맞춰 정당화하지 않는다.

## 2. 문서 상태와 변경 기록

- 화면 원칙을 고른 앱의 문서 상태는 한글로 쓰고, 확인하지 못한 정보는 `미확인` 으로 적는다.
- 그 밖의 앱에서 문서 상태 관례가 없으면 `Active`(현행), `Planned`(계획), `Deprecated`(폐기 예정), `Superseded`(대체됨), `N/A`(해당 없음), `TBD`(미정), `NOT VERIFIED`(미확인)를 쓴다. `Planned` 는 가까운 실제 계획에만, `N/A` 는 적용 대상이 아닌 까닭과 함께 쓴다.
- 프로젝트에 변경 기록 파일이 있으면 쓰는 사람이 알아챌 변화는 같은 묶음에서 그 파일의 다음 판 절에 영향 중심으로 한 줄 적는다.

## 3. 용어와 고정 문구

- 화면 문구에는 회사 문서나 다른 업무 앱에서 이미 쓰는 업무 용어를 쓰고, AI 가 지어낸 말을 쓰지 않는다. 같은 개념에는 같은 용어를, 같은 뜻에는 같은 상태 낱말을 쓴다.

```text
피함: 장비 ID / 기기 번호 / Set 번호 / Set ID 를 화면마다 섞어 씀
좋음: 프로젝트에서 권위 있게 정한 하나의 용어
```

- 용어는 지금 명세·제품·API 의 권위 용어 → 현장 업무 용어 → 공급자·프로토콜의 공식 용어 → 중립적이고 구체적인 표현 차례로 고른다.
- 활동·알림·오류는 고정 틀이나 번역 자원과 실제 동적 값으로 짓는다. 프로그램이 쓰는 기본 문구를 AI 나 무작위 표현으로 그때그때 바꾸지 않는다. 예: 고정 이름표 `저장 완료` 와 실제 건수 `3`(피함: `멋지게 저장됐습니다!`). 실제 실패를 고정 성공 문구로 가리지 않는다.
- 실제 자료·사용자가 쓴 글·핵심 생성 기능은 고정하지 않는다. 동적 생성이 제품 기능이면 그 범위를 사용자에게 확인한다.
- 경고·파괴적 확인·로그·시험 실패 메시지·운영 문서는 결과·식별자·조건을 재현에 필요한 만큼 남긴다(피함: `저장 후 변경 불가`, 필요한 경우: `저장 후에는 장비 유형을 변경할 수 없습니다.`). 화면 원칙을 고른 앱의 화면에는 이 문장을 두지 않고 로그·시험 실패 메시지·운영 문서에만 쓴다.

## 4. 화면 계약

- 기능 하나가 여러 화면을 거치면 화면 사이의 전환과 효과를 한 줄로 적는다. 기존 계약이 그 흐름을 설명하면 다시 적지 않는다.

`흐름 | 진입 위치 | 거치는 화면과 단계(단계 수의 까닭) | 데이터·권한 | 실패·취소(취소 때 되돌림) | 완료 뒤 반영(다른 화면에 미치는 효과, 메인 표시 범위) | 작은 화면·키보드`

- 저장 뒤 메인 갱신처럼 한 화면의 동작이 다른 화면을 바꾸는 효과는 이 줄 한 곳에만 적는다. 팝업·확인 단계는 단계마다 없애면 무엇이 깨지는가를 적는다. 까닭은 이 설계 기록에 두고 화면·툴팁·오류 문구에는 넣지 않는다.
- 사용자가 정하지 않은 보이는 동작(저장이 실패하거나 취소했을 때 보이는 것, 누가 바꿀 수 있는지 같은 권한)은 먼저 같은 앱에서 같은 상황을 처리한 선례를 찾아 따른다. 선례가 없으면 정해진 것처럼 적지 않고, 토론으로 정한 제안값을 적고 `제안 · 결정 필요` 로 표시해 그 기능의 다른 결정 질문과 한 묶음으로 묻는다.
- 누름 영역·화면 폭 기준점·움직임 길이 같은 수치는 꼬리표를 붙여 성격을 가른다: 프로젝트 토큰·설정은 `FACT`, 적용 범위를 확인한 공식 플랫폼·접근성 기준은 `STANDARD SNAPSHOT`, 화면 경험값은 `HEURISTIC`, 대표 화면 크기 같은 설명용 값은 `EXAMPLE`.
