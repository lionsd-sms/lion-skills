# 앱 확인 절차

앱마다 실제로 띄워 사용자처럼 조작하고 증거를 남기는 절차를 프로젝트 안에 두고, 앱이 바뀔 때마다 돌려 보며 고친다.

## 바로 할 일

1. 프로젝트 규칙 문서와 docs 에서 기존 확인 절차를 찾는다. 있으면 아래 「점검」으로 간다. 없으면 2번부터 만든다.
2. 저장소에서 먼저 알아낸다: 사용자가 만지는 면(창·웹 화면·명령줄·API), 실행 명령과 준비된 신호, 쓸 수 있는 조작 수단, 남길 수 있는 증거, 둘을 나란히 띄울 수 있는지. 코드·README·스크립트로 알 수 없는 것만 사용자에게 묻는다.
3. 절차 파일 하나를 쓴다. 자리는 프로젝트 규칙 문서가 가리키는 docs 아래 한 파일이고, 가리키는 곳이 없으면 그 프로젝트의 이름 관례로 docs 에 만든다. 절차에 스킬 이름을 적지 않는다. 아래 여섯 칸을 이 저장소의 실제 명령·이름으로 채우고 빈칸을 남기지 않는다.
   - 실행: 빈 자료 폴더에서 사용자가 조작할 수 있는 상태까지(마이그레이션·기초 자료 포함). 첫 화면이 조작 가능해지는 신호를 준비됨으로 적는다.
   - 상태 점검: 읽기 전용 확인 하나. 내가 띄운 프로세스인가, 방금 만든 빌드인가, 확인용 자료 폴더인가, 로그인이 살아 있나. 첫 조작 전과 이상한 일 뒤마다 돌린다.
   - 조작: 사용자가 실제로 쓰는 버튼·메뉴·단축키·명령. 접근 이름·라벨·명령 문자열 같은 안정된 손잡이를 쓰고 좌표·탭 순서는 쓰지 않는다. 내부 함수나 시험 전용 주소로 값을 넣은 결과는 확인으로 치지 않는다.
   - 증거: 동작과 그 뒤 상태를 함께 남긴다. 화면(앱 이름이 보이는 캡처), 값(저장된 값을 두 번째 읽기 전용 경로로 읽음), 로그·종료 코드. 남기는 폴더를 적는다.
   - 정리: 이번에 띄운 것만 PID 로 끈다. 인스턴스와 임시 자료는 지우고 증거는 남긴다.
   - 기능 지도: 기능 → 들어가는 길 → 확인 경로 → 끝 상태. 처음에는 사용자에게 보이는 기능 3~5개로 시작한다.
4. 넘기기 전에 절차를 한 번 끝까지 실제로 돌린다: 실행 → 상태 점검 → 지도의 기능 하나 조작 → 증거 → 정리 → 정리 뒤 증거가 그 폴더에 남았는지 확인. 실패하면 절차를 고치고, 실패한 시도마다 정리를 돌린다. 끝까지 돈 뒤에 프로젝트 규칙 문서의 「실행·시험 명령」 절에 절차 파일 경로 한 줄을 더한다. 한 번도 돌리지 못한 절차는 초안으로 보고하고 경로 줄을 더하지 않는다.
5. 제품 코드는 고치지 않는다. 쓰는 곳은 절차 파일, 그 곁의 도움 스크립트, 프로젝트 규칙 문서의 경로 한 줄이다. 앱이 빌드·실행되지 않으면 막힌 명령과 오류를 그대로 보고하고 멈춘다.

화면 조작 수단이 없으면 화면 아래 층(화면이 부르는 명령·API, 저장된 값, 로그)으로 확인할 수 있는 것을 확인하고, 화면 경로는 확인 못 함으로 적는다. 화면 단계는 사용자에게 눌러 달라고 하고 그 뒤 상태를 값·로그로 읽을 수 있다.

## 점검

이미 절차가 있으면 지도의 모든 기능을 소스로 읽고 실제로 한 번 이상 조작해 본 뒤, 결과를 셋 중 하나로 말한다.

- 그대로: 모든 기능을 소스와 실행으로 확인했고 고칠 것이 없다.
- 바뀜: 확인을 거친 고침을 절차에 반영했다.
- 막힘: 확인을 끝내지 못했다. 막은 명령·전제를 적는다.

지도와 다르게 동작하면 가른다. 커밋·결정 기록·함께 바뀐 화면 문구가 의도된 변경을 보이면 문서가 낡은 것이니 지도를 고친다. 의도된 근거가 없으면 제품이 회귀한 것이니 사용자에게 알리고 지도는 그대로 둔다. 동작은 맞는데 절차로 조작이 안 되면 조작 방법을 고치고 다시 돌려 확인한다.
