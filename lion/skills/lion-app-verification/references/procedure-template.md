# 절차 꼴

절차 파일은 그 앱을 처음 보는 AI 가 작업 도중에 열어 그대로 따라 할 수 있게 쓴다. 모든 명령은 이 저장소에서 실제로 돌아가는 글자 그대로 적는다.

목차: 1. 절차 파일 꼴 · 2. 기능 지도 항목 꼴 · 3. 앱 종류별 수단 · 4. 증거를 세우는 기준

## 1. 절차 파일 꼴

머리에 앱 이름, 확인 대상 면(창·웹 화면·명령줄·API), 이 파일을 여는 때 한 줄을 둔다. 그 뒤 절 순서는 실행 · 상태 점검 · 조작 · 증거 · 정리 · 기능 지도다.

| 절 | 적을 것 |
|---|---|
| 실행 | 준비 명령(의존성 설치·빌드)은 한 번, 띄우는 명령, 확인용 자료 폴더를 정하는 방법, 기초 자료 넣기, 준비됨 신호(로그 한 줄·창 제목·첫 화면 요소). DB 가 응답해도 초기화 스크립트가 아직 돌 수 있으니 준비됨은 첫 화면 조작 가능으로 잡는다. 짧게 끝나는 CLI 는 빌드 한 번 뒤 실행마다 새 임시 폴더를 쓴다. |
| 상태 점검 | 읽기 전용 명령 하나 또는 짧은 묶음. 프로세스가 이번에 띄운 PID 인가, 빌드가 방금 만든 것인가(판 번호·빌드 시각), 포트·창이 우리 것인가, 자료 폴더가 확인용인가, 로그인이 살아 있나. |
| 조작 | 쓰는 도구와 손잡이 규칙. 접근 이름·라벨·data 속성·메뉴 글자·명령 문자열. 둘을 나란히 띄울 수 없으면 사용자가 켜 둔 앱은 조작하지 않는다고 적는다. |
| 증거 | 남길 것(캡처·접근성 트리·명령과 stdout·stderr·종료 코드·저장된 값·로그 조각)과 폴더. 폴더는 git 에 올리지 않는 곳으로 정하고 정리가 지우지 않는다. 파일 이름에 기능 ID 와 들어간 길을 넣는다. |
| 정리 | 이번에 띄운 PID 끄기, 확인용 자료 폴더 지우기, 기초 자료 되돌리기. 프로세스 이름으로 끄지 않는다. 정리 뒤 증거 폴더가 남았는지 확인하는 명령. |
| 기능 지도 | 목차와 기능 항목(2절). 기능이 많아 파일이 길어지면 기능마다 파일을 나누고 이 절은 목차만 둔다. |

도움 스크립트를 두면 절차 파일 곁에 두고, 실행 권한을 주고, 부르는 명령을 절차 본문에 적는다. 읽는 쪽이 스크립트를 뜯어봐야 쓸 수 있으면 다시 쓴다.

앱 실행을 막는 것이 확인과 무관한 빈 자료(예시 설정 파일, 쓰지 않는 정적 폴더)뿐이면 절차의 실행 절에서 만들고 정리 절에서 지운다. 확인용으로 만든 것이라고 적는다.

## 2. 기능 지도 항목 꼴

기능마다 제목과 한 문단(사용자에게 보이는 동작)을 두고, 네 칸을 이 순서로 쓴다.

1. 세부 기능: 짧은 ID 와 한 줄 설명. 예 `item-add-save` 품목 이름과 수량을 저장한다.
2. 들어가는 길: 사용자 쪽에서 본 모든 입구. 버튼, 단축키, 메뉴, 명령.
3. 확인 경로: `전제:` 줄로 시작하고, 줄마다 사용자 동작 · 실제 명령 · 보이는 결과를 짝지어 쓴다. 마지막 줄은 증거 남기기.
4. 함정: 확인을 헛되게 하거나 틀린 결론을 내게 하는 것.

지키는 것:

- 구현 세부(함수 이름, 내부 상태)는 적지 않는다. 사용자 경로, 손잡이, 필요한 상태, 명령, 보이는 결과만 적는다.
- 기초 자료에 전제가 없으면 그 경로는 실패로 보고하고 까닭을 함정에 적는다. 통과시키려고 경로를 줄이지 않는다.
- 입구가 여럿이면 모두 적는다. 한 입구로 확인한 결과를 다른 입구의 확인으로 적지 않는다. 닿지 못한 입구는 시도한 명령과 빠진 전제를 적는다.
- 저장하는 기능은 다시 열거나 저장소를 읽어 값이 남았는지까지 본다.

## 3. 앱 종류별 수단

| 종류 | 실행·준비됨 | 조작 | 증거 |
|---|---|---|---|
| Windows 데스크톱(Tauri) | 디버그 또는 배포 빌드 exe. 창 제목·로그 줄·첫 화면 요소 | WebView2 원격 디버깅 포트(`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`)에 CDP 로 붙는 Playwright, tauri-driver(WebDriver), AI 의 화면 조작 도구. 웹뷰 밖 창은 화면 조작 도구 | 캡처, 앱 자료 폴더의 파일·DB 읽기 전용 조회, 로그 |
| 다른 데스크톱(Electron 등) | 실행 파일·개발 명령 | `--remote-debugging-port` 와 CDP, 없으면 화면 조작 도구 | 위와 같음 |
| 웹 | 개발 서버 명령, 포트가 열리고 첫 화면이 그려진 때 | 브라우저 자동화(역할·라벨 손잡이) | 캡처, 접근성 트리, 네트워크 응답, 저장된 값 |
| CLI·TUI | 빌드 한 번, 실행마다 새 임시 폴더 | 명령 실행. 대화형은 의사 터미널(pty)·expect 류 | 명령, stdout, stderr, 종료 코드, 만든 파일 |
| 서버·API | 띄우는 명령, 헬스 주소와 마이그레이션 끝 신호를 함께 | HTTP 요청(curl·Invoke-RestMethod) | 상태 코드, 응답 본문, 저장된 값의 두 번째 읽기 |
| 라이브러리 | 빌드 | 공개 API 를 부르는 작은 예제 프로그램 | 출력, 만든 파일 |

한 저장소에 면이 여럿이면 사용자가 주로 쓰는 면을 첫째로 쓰고 나머지는 머리에 적는다.

## 4. 증거를 세우는 기준

- 진짜를 직접 본다. 프로세스는 PID 로, 값은 저장소에서 읽는다. 파일 수정 시각, 이전 캡처, 작업자의 "됐다"는 말은 증거로 치지 않는다.
- 확인이 실패하면 관찰 방법(포트·선택자·대기)을 먼저 의심하고, 그다음 앱을 의심한다.
- 화면 갱신은 결과 요소나 상태 글자가 나타날 때까지 기다린다.
- 부작용(쓴 파일, 넣은 줄, 보낸 메시지)을 보이는 화면과 함께 확인한다.
- 드라이런·시험 모드를 쓰면 실제로 무엇을 건너뛰는지 파일·네트워크·git 상태를 보고 확인한다.
- 가짜 대상(mock)은 실제 제품에서도 외부 시스템이 경계 너머에 있는 자리에만 쓴다.
- 되풀이할 확인은 스크립트로 만들어 돌리고 출력을 증거 폴더에 남긴다.
- 실제 대상 대신 다른 자리(설치본 대신 개발 빌드, 새 PC 대신 기존 PC)에서 돌렸으면, 그 자리가 미리 해 준 준비 단계를 적고 실제 대상에서 돌리기 전까지 확인 못 함으로 둔다.
