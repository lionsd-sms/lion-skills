# 원인 가르기와 고침

재현 수단이 있고 가설을 가르거나, 회귀·방어 코드의 내력을 찾거나, 느림을 고칠 방법을 고를 때 쓴다.

## 1. 가르기

- 남은 문제 범위를 가장 많이 자르는 갈래부터 실행 증거로 확인해 후보를 지운다. 살아남은 하나의 기전을 실행 증거로 확인한 뒤 고친다.
- 사용자가 아는 것(최근 배포, 이미 배제한 원인)이 가설 순위를 바꿀 수 있으면 가설 목록을 한 번 보이고, 답을 기다리지 않고 진행한다.
- 도구는 디버거·REPL 확인 → 가설을 가르는 경계의 표적 로그 차례로 고른다. 전부 찍고 검색하는 로그는 쓰지 않는다.
- 임시 디버그 로그에는 `[DEBUG-a4f2]` 같은 고유 꼬리표를 붙인다. 끝내기 전에 `[DEBUG-` 검색 결과가 0인지 확인한다.
- 성능 회귀는 로그 대신 기준 측정(시간 측정 틀·프로파일러·실행 계획)을 잡고 이분 탐색한다.

## 2. 고칠 자리

근본 원인은 시스템이 하지 말아야 할 일을 처음 한 자리, 또는 다뤄야 할 상태를 처음 다루지 못한 자리다.

- 증상을 낸 상태가 정당한지 묻는다. 시스템이 그 상태에 있을 수 있으면 그 상태에서 깨진 코드가 원인이고 거기서 다루는 것이 고침이다. 있을 수 없는 상태면 깨진 자리의 검사는 버그를 가린다. 그 상태를 만든 곳을 찾는다.
- 막기·재시도·삼킨 오류·값 잘라 맞추기·상태 버리기는 버그를 가리는 흔한 꼴이다. 이것을 넣으려면 그 상태가 정당하다는 근거를 댄다.
- 같은 결함이 있는 자리를 모두 찾아 함께 고친다. 우회를 설명하는 주석이 한 문단이 필요하면 코드를 고친다.
- 결정적 사실을 찾는 데 깊이 파야 했으면, 처음 볼 때 그것을 보여 줄 싸고 늘 켜진 신호를 보고에 제안한다.

예: 사용자 목록에 같은 사람이 두 번 나온다. 화면에서 중복을 걸러 내면 증상만 사라진다. 원인은 API의 결합(JOIN)이 행을 불린 것이고, 질의나 자료 모델을 고친다. `DISTINCT`로 잘못된 결합을 덮는 것도 덧대기다.

## 3. 전제 시험

같은 전제를 깐 고침 두 개 이상이 같은 확인에서 실패하면 고침보다 전제를 의심한다.

1. 실패한 고침들이 모두 가정한 한 문장을 적는다.
2. 그 전제가 틀렸다면 다르게 나올 관찰을 골라 직접 확인한다. 실패의 크기와 함께 분포(어느 경우에 몰리나)를 본다. 이 확인은 다시 돌릴 수 있게 남긴다.
3. 전제가 반박되면 전제가 예측하지 못한 실패들의 공통점을 찾는다. 전제가 맞으면 "왜"를 한 단 더 묻는다. 앞 고침들은 결과를 다뤘을 수 있다.
4. 원인 조건을 없애는 쪽으로 고친다. 뒤에서 치우는 장치는 원인을 두고 매번 일을 더한다.

## 4. 회귀 시험 자리

회귀 시험은 실제 버그 꼴을 호출처에서 일어나는 그대로 재현하는 자리가 있을 때만 쓴다. 호출처 여럿이 얽혀야 나는 버그를 단일 호출 시험으로 잡으면 거짓 안심을 준다. 그런 자리가 없으면 그 사실을 발견으로 보고한다. 코드·픽스처를 일부러 바꿔 실패를 냈으면 원본과 비교해 그 변경이 실제로 들어갔는지 확인한다. 커밋을 맡았고 나눌 수 있으면 실패하는 재현을 고침보다 먼저 남긴다.

## 5. 변경 이력 조사

회귀가 언제 들어왔는지, 이상해 보이는 방어 코드(널 검사·재시도·시간 제한·기능 스위치)가 왜 있는지 알아야 할 때 쓴다. `git blame`·`git log --follow`로 최근 커밋에서 멈추지 않고 그 줄이 처음 들어온 커밋까지 거슬러 간다. 방어 코드라면 그 무렵의 사고·장애 기록을 함께 찾는다.

주장마다 하나의 확신 등급에 둔다.

| 등급 | 뜻 | 쓰는 꼴 |
|---|---|---|
| 직접 | 작성자가 까닭을 글로 남김(PR 본문·이슈·주석·설계 문서·대화) | "X 때문에 있다" + 인용 |
| 뒷받침 | 간접 근거 여럿이 한 결론으로 모임 | "근거 a·b·c가 X를 가리킨다" |
| 추론 | 맥락으로 읽은 해석 | "A와 B로 보아 C일 가능성이 높다" + 추론 사슬 |
| 추측 | 다른 설명도 똑같이 맞는 가설 | 경쟁 가설 목록에 둔다 |
| 모름 | 찾았으나 없음 | 찾은 곳과 검색어를 구체로 적는다 |

- 코드 자체를 그 코드의 의도에 대한 근거로 쓰지 않는다.
- 사용자가 질문에 붙인 짐작은 후보 하나로 두고 따로 확인한다. 근거끼리 어긋나면 둘 다 인용한다.
- "아무도 까닭을 적지 않았다"도 결과다. 빈 곳이 하나도 없는 보고는 다시 본다.

## 6. 느림을 고칠 방법

고칠 방법은 싼 것부터 차례로 따져 앞 단계로 목표에 닿으면 멈춘다.

1. 결과를 아무도 쓰지 않는 일은 없앤다.
2. 한 번 한 일은 저장해 다시 쓴다.
3. 덜 한다(범위·횟수·크기 줄이기).
4. 나중에 한다(필요할 때 처음 계산).
5. 사용자가 기다리지 않을 때 한다(빈 시간·뒤에서).
6. 동시에 한다.
7. 더 싸게 한다(알고리즘·자료 구조·질의).
