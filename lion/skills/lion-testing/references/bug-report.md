# 버그 판정과 QA 시트

결함 판정이나 시험·결함 보고서, 테스트케이스 시트의 작성·검토에 쓴다. 관찰·시험 기록·사양·사용자 설명을 구분한다. 관찰되지 않은 버그·원인·숫자를 채워 넣지 않는다. "재생이 끊겼다"는 관찰만으로 "네트워크 지연 때문"이라고 쓰지 않는다. 현재 구현만으로 의도된 동작을 확정하지 않는다.

## 1. 요청에 맞는 깊이

| 요청 | 처리 |
|---|---|
| 새 리포트·케이스 작성 | 근거를 모아 결함 여부와 기존 행을 판별한 뒤 양식에 배치하고 확인한다 |
| 기존 리포트 검토 | 근거와 각 행을 대조한다. 근거가 없으면 내부 중복·모순·빈 칸·예상/실제 결과의 불일치만 짚고 진짜 결함 판정은 보류한다 |
| 문체·양식만 정리 | 기존 사실·판정·사용자 손편집을 유지한다. 판정을 다시 하지 않는다 |
| 단건 판별 | 재현·사양·최신 상태의 근거로 답한다. 부족하면 필요한 관찰을 특정하고 판정을 보류한다 |

## 2. 판정

- 원본 기록·스크린샷·구술·기존 보고서의 시간 순서를 확인한다. 뒤에 수정·재확인이 있으면 최신 상태를 판정에 반영하고 발견 경과는 남긴다.
- 후보마다 정상 동작인지, 사양으로 정한 동작인지, 이미 고쳐졌는지, 다른 후보와 같은 결함인지, 기존 행에 있는지, 근거가 충분한지 확인한다. 비슷한 증상만으로 합치지 않고 재현 조건과 결과를 대조한다. 범용 UI 관례로 현장 고유 동작을 정상이라고 단정하지 않는다.
- 예상 결과는 사양·원본 기록·사용자 확인에서 받아 관찰한 실제 결과와 짝짓고, 판·장비·현장·입력·조작 순서 같은 재현 조건을 함께 둔다. 추정 원인은 추정으로 표시한다.
- 근거가 부족하거나 원본끼리 수치·시점·정상 기준이 충돌하면 차이를 보여 주고 필요한 사실만 묻는다. 지금 확인할 수 없는 후보는 `검증 필요`로 남기고 판정 칸을 비운다. `FAIL`을 미확인의 대신으로 쓰지 않는다.
- 정상으로 실제 확인된 항목은 판정 칸이 있는 테스트케이스 양식에서 `PASS`로 쓴다. 결함만 나열하는 보고서에서는 뺀다. 사용자가 정한 판정이나 손편집을 바꾸거나 작성된 케이스를 빼기 전에는 대상·이유·근거를 보여 주고 확인받는다.

## 3. 양식과 값

- 기존 헤더·작성 예시·용어·셀 스타일을 따른다. 예상 결과와 실제 오류, 사전조건과 시험 데이터, 판정과 근거가 각각 맞는 칸에 들어가게 한다. 심각도·우선순위·담당·기한은 근거 없는 값으로 채우지 않는다.
- 케이스 ID는 기존 접두어·자릿수·연번을 이어 쓰고 결번·외부 참조를 보존한다. 새 양식에 식별 규칙이 없거나 기존 행의 순서를 바꿔야 하면 사용자가 정할 부분을 확인한다.
- 수치·판·환경은 원본의 값만 쓴다. 다른 기록이 다른 값을 말하면 양쪽을 제시하고, 확인 전에는 `수치 확인 필요`로 둔다. 예시 숫자를 실제 관측값으로 옮기지 않는다.

## 4. 파일을 고칠 때

- 행을 삭제하거나 옮기면 수식·이미지·조건부 서식·데이터 검증·외부 참조가 어느 케이스를 가리키는지 확인한다. 소스와 보고서가 같은 워크북의 다른 시트에 있으면 변경 대상 밖의 시트까지 대조한다.
- 저장한 파일을 다시 열고 최종 행마다 중복·판정·예상/실제 결과·재현 조건·스크린샷 연결을 원본과 대조한다. 실제 재현·수정 확인을 하지 않았으면 문서 검토와 실행 검증을 구분한다.
- 작성된 케이스를 뺐으면 기존 문구와 뺀 이유를 제출본 밖의 같은 작업 위치에 남겨 복구할 수 있게 한다.
