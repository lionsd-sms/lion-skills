# 올림 한 장

## 1. 쓰는 때

다시 보기 뒤 아래 가운데 하나가 있으면 검수를 맡긴 쪽(한 단 위)에 올림 한 장을 보낸다.

- 부분 · 미해소로 남은 지적
- 다시 볼 때 새로 나온 높음
- 만든 쪽이 근거를 대고 받지 않은 지적
- 검수 막힘(자료·권한·도구가 없음)

## 2. 한 장 꼴

```
올림: <일 이름> 검수에서 남은 것 n건
판본: <다시 본 판본>

[1] 저장 실패 때 입력이 지워짐 (높음 · 부분 · src/save.ts:44)
    검수 쪽: 실패 뒤 입력이 남아야 한다 — 근거: 요청 원문 "저장 실패해도 입력은 남긴다"
    만든 쪽: 연결 끊김만 남기고 서버 거절은 비운다 — 근거: 서버 거절은 다시 보내도 같은 결과
    가릴 길: 없음(사용자가 보는 결과가 달라짐)
    추천: 가) — 까닭: 요청 원문이 실패 종류를 가르지 않음
    고르면 달라지는 것:
      가) 실패는 모두 입력을 남긴다 → 사용자가 고쳐 다시 보냄, 고칠 곳 한 군데
      나) 서버 거절은 비운다 → 같은 내용을 다시 보내는 일이 없음, 사용자는 처음부터 다시 입력
```

- 남은 것은 한 줄로, 등급 · 다시 본 결과 · 위치를 괄호에 붙인다.
- 양쪽 근거는 각자의 주장과 그 근거를 한 줄씩 쓴다. 근거는 파일:줄, 시험 출력, 요청 원문 인용이다.
- 가릴 길은 시험·자료로 가릴 수 있으면 그 방법을, 없으면 무엇이 달라지는지(결과·범위·취향·정책·비용)를 쓴다.
- 추천은 하나를 고르고 까닭 한 줄을 붙인다.
- 고르면 달라지는 것은 안마다 사용자가 볼 결과와 남는 일을 쓴다.
- 비슷한 것은 한 번호로 묶는다.

## 3. 받은 쪽이 할 일

```
올림 받음
 ├ 시험·자료로 가릴 수 있다
 │   → 직접 시험을 돌리거나 자료를 열어 정함
 │   → 만든 쪽이 그 결정대로 고침 → 정한 쪽이 실제로 확인 → 끝
 └ 보이는 결과 · 범위 · 취향 · 정책 · 비용이 달라진다
     → 같은 한 장에 「받은 쪽 의견」 한 줄을 붙여 한 단 위로 올림
         └ 마스터까지 오면 → 사용자에게 객관식
```

- 양쪽 근거가 부딪치면 이 순서로 가린다: 사실·시험 출력·원자료 → 프로젝트 규칙 문서와 서식 규칙 → 설계 원칙(정확성·읽는 부담·덜 짓기) → 기존 관례와의 일관성. 앞 칸에서 갈리면 뒤 칸은 보지 않는다.
- 정한 내용은 끝 보고에 적는다. 오래 남을 결정이면 프로젝트 규칙 문서의 「정해진 결정」 절에 날짜와 까닭을 남긴다.
- 정한 뒤의 고침은 새 검수 왕복을 열지 않는다. 정한 쪽이 바뀐 동작을 실제로 확인한다.

## 4. 사용자에게 묻는 꼴

마스터가 올림 한 장을 사용자 질문으로 바꾼다.

- 하나씩 묻고, 비슷한 것은 묶어 한 번에 넷까지.
- 사용자가 볼 결과로 쓴다. 파일 이름·함수 이름·개발 용어는 빼고 작업 기록에만 둔다.
- 추천안을 첫째에 두고 「(추천)」 을 붙인다. 안마다 고르면 달라지는 것을 한 줄로 쓴다.
- 질문 끝에 「추천대로면 '응'」을 쓴다. '응'·'좋아'·'그렇게 해'처럼 번호 없이 동의하면 추천을 고른 것으로 받고 받은 값을 한 줄로 알린다. 추천이 없는 질문에 번호 없이 답하면 다시 묻는다.
- 양쪽 주장은 한두 줄로 보인다.

```
검수에서 남은 것이 하나 있습니다.

저장이 실패하면 적어 둔 내용이 지워집니다.
검수 쪽은 실패하면 늘 남겨야 한다고 보고, 만든 쪽은 서버가 거절한 경우는 비우는 편이 낫다고 봅니다.

1) 실패하면 늘 남긴다 (추천) — 적은 내용을 고쳐 다시 보낼 수 있습니다.
2) 서버가 거절한 경우만 비운다 — 같은 내용을 다시 보내는 일이 없고, 처음부터 다시 적어야 합니다.
3) 지금은 두고 끝 보고에 남긴다 — 이번 작업은 지금 상태로 끝납니다.

추천대로면 '응'.
```

- 사용자 답은 결정 기록에 남기고 다시 묻지 않는다. 만든 쪽이 그대로 고치고 마스터가 실제로 확인한다.
