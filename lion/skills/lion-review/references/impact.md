# 변경 파급 확인

작은데 믿기 어려운 변경, 공유 구조·자료 형식·되돌리기 어려운 변경을 검수할 때 쓴다. 호출처 목록은 검색으로 바로 나오므로 결과로 내지 않는다. 검색이 놓치는 깨짐을 찾는다. 그럴듯한 설명 글은 맞든 틀리든 그럴듯하게 읽히므로, 안전 근거가 되는 사실 한두 개를 코드를 돌려 증명한다.

## 1. 확신 단계

안전 근거가 되는 사실마다 아래 단계 가운데 어디까지 갔는지 적는다.

1. 말함. 혼자서는 근거가 되지 않는다.
2. 줄을 짚음. 실제 파일:줄이나 라이브러리 원문.
3. 나쁜 경우가 일어나지 않음을 단계별로 따라가 보임.
4. 돌림. 실제 코드를 부르고 틀리면 크게 실패하는 스크립트·시험.
5. 실행 중인 앱에서 재현함.

4단계는 보통 앱이 쓰는 라이브러리를 그대로 불러 걱정되는 함수를 직접 부르는 작은 스크립트 하나다. 스크립트는 허용된 사본이나 임시 폴더에 두고 대상 파일은 고치지 않는다.

## 2. 순서

1. 변경을 읽는다. 더하고 바꾸고 지운 이름, diff 에 드러나지 않는 달라진 동작까지.
2. 안전 근거 사실 하나를 찾는다. 위험해 보이는 변경 대부분은 사실 하나 덕분에 안전하다. 예: "이 호출은 이미 만료된 캐시 항목만 지운다". 그 사실이 맞으면 위험 대부분이 한 번에 걷힌다. 긴 가능성 목록보다 이 사실에 시간을 쓴다.
3. 검색이 멈추는 곳을 본다. 부르는 라이브러리의 원문과 고정된 판·로컬 패치, 실행 시점(마이크로태스크, 해제·정리 순서), API 가 돌려주는 JSON, DB 열, 전송 형식, 같은 바이트를 읽는 다른 언어, 기능 플래그, 세 단계 아래 코드.
4. 위험마다 일어날 가능성과 일어났을 때 드는 값을 적는다. 확인된 위험과 확인해서 걷힌 위험을 따로 적는다. 찾아서 없는 것도 결과다. 호출처나 API 를 지어내지 않는다.
5. 안전 근거를 4단계까지 증명하고 돌린 명령과 출력을 붙인다. 못 했으면 「증명 못 함」으로 적는다.
6. 변경이 넓으면 영역을 나눠 검수자 여럿에게 같은 질문을 맡긴다.

## 3. 답 꼴

```
하는 일: <바뀐 것, 드러나지 않는 부분 포함>
안전 근거: <사실> — <단계 n> — <증명: 명령과 출력 | 증명 못 함>
위험:
[1] <어떻게 깨지나> · <파일:줄> · 가능성 <높음·중간·낮음> · 드는 값 <…> · 확인 방법
걷힌 위험: <확인한 것과 괜찮은 까닭>
합치기 전 시험: <진짜 버그를 잡을 가장 싼 시험이나 재현, 쓴 스크립트 경로>
```

- 확인된 위험을 지적으로 낼 때는 등급과 축을 단다.
- 증명하지 못한 안전 근거는 「못 본 범위」에 적는다. 그 사실이 틀릴 때 데이터 손실이나 기존 기능 깨짐이 생기면 끝 보고 첫머리에 둔다.
