# 코드 검수 볼 곳

결과물이 코드일 때 세 축(요구 대조 · 기준 · 덜 짓기)을 이 목록으로 읽는다. 대상에 맞는 항목만 쓴다. 한 줄 버그 수정이면 1 · 2절이면 된다.

## 1. 시험부터

- 바뀐 동작마다 시험이 있는지, 시험이 구현 세부보다 동작을 보는지 본다.
- 시험이 회귀를 잡는지는 실험으로 정한다. 허용된 사본에서 바뀐 조건 하나를 뒤집고(부정 빼기, 그리고↔또는) 시험을 돌린 뒤 원래대로 되돌린다. 뒤집어도 통과하면 빠진 시험 사례를 이름으로 대어 지적한다(중간).
- 버그 수정에 그 버그를 재현하는 시험이 없으면 지적한다. 연결 경계를 건드렸으면 끝까지 이어진 경로를 시험하는지 본다.
- 확인 기록을 본다: 돌린 시험, 빌드, 화면 변경의 전후 화면. 없는 것은 「못 본 범위」에 적고, 요청이 그 확인을 요구했으면 지적한다.
- 코드나 시험이 완료 · 살아 있음을 파일 수정 시각, 캐시, 하위 실행의 자기 보고로 판정하면 지적한다. 실제 값과 실제 산출물을 읽게 한다.

## 2. 증상 덮기

고친 자리가 원인을 고쳤는지 본다. 바뀐 파일 밖의 호출처 · 피호출처 · 자료형 정의를 열어 이 변경이 맞는 층에 있는지 판단한다.

- 불변 조건 위반을 가리는 조기 반환, 깨진 약속을 숨기는 재시도, 모델링 오류를 끄는 형 변환, 불분명한 조건을 덮는 조용한 기본값.
- A 모듈에서 막았는데 고칠 곳은 B 모듈의 약속인 경우.
- "X 하지 말 것" 주석이나 외워야 하는 관례로 막은 것. 자료형 제약 · 검사 규칙 · 실행 검사로 틀린 길을 막을 수 있으면 방향에 적는다.
- 정확성 · 보안 규칙을 끄는 억제 주석(eslint-disable, @ts-ignore 같은 것)은 중간 이상.
- 버그 의심은 호출 경로를 따라가 그 값이 실제로 오는 길을 보인다. 위에서 검증하거나 자료형이 막으면 지적하지 않는다.

## 3. 구조와 읽는 부담

- 새로 온 사람이 "X 는 어디서 오나, 무엇이 X 를 바꾸나"를 30초 안에 답하지 못하면 지적한다.
- 리팩터는 읽는 사람이 들고 있을 개념 수가 줄어야 나아진 것이다. 같은 복잡도를 옮기기만 했으면 지적하고, 분기 · 모드 · 층이 사라지는 꼴을 방향으로 쓴다.
- 관련 없는 흐름에 끼운 새 조건문, 같은 모양을 두고 되풀이되는 조건 사슬은 설계 지적(중간)이다.
- 기능 고유 논리가 공유 모듈에 들어감, 이미 있는 대표 도우미와 거의 같은 것을 새로 만듦은 중간이다.
- 1,000줄 아래 파일을 1,000줄 넘게 키우면 지적하고, 먼저 쪼갠 뒤 더하는 방향을 쓴다.

## 4. 덜 짓기

- 두 번째 쓰임이 없는 추상화 · 매개변수 · 설정 · 훅, 호출처 하나뿐인 감싸기. 추상화를 더하라는 지적도 두 번째 쓰임이 있을 때만 낸다.
- 새 API 를 만들고 외부 사용처가 없는 옛 길을 남김. 호출처를 옮기고 같은 변경에서 옛 길을 지우는 방향을 쓴다.
- 이제 쓰이지 않는 함수 · 상수 · 호환 층, 지운 흔적 주석은 지울 목록으로 적는다. 지우기는 만든 쪽이 확인한 뒤 한다.
- 판 올리기를 한 변경에 여럿 묶었거나 잠금 파일을 손으로 고쳤으면 지적한다.

## 5. 주석

프로젝트 규칙 문서가 주석 규칙을 정했으면 그것을 따른다. 정하지 않았으면 아래로 본다.

- 남길 주석: 라이선스 머리말, 바꿀 수 없는 외부(의존성 · 플랫폼 · 규약)가 강요한 뜻밖의 동작, 서식 도구 제외 표시, 공개 API 약속 설명, 코드로 쓸 수 없는 제약을 설명하는 이슈 · RFC 링크.
- 그 밖의 설명 주석은 낮음이다. 우리 코드의 뜻밖의 동작을 변명하는 긴 주석이 붙어 있으면 그 코드를 이름 · 추출 · 자료형으로 동작이 드러나게 바꾸는 구조 지적(중간)으로 낸다.
- 「지우지 말 것」「바꾸기 전에 물어볼 것」 같은 제약 주석은 자료형 · 시험 · 검사 규칙으로 옮길 수 있으면 방향에 적는다.
