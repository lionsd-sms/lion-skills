# 저장소 작업

커밋 꼴·스테이징·복구 기준점·push·태그를 다룰 때 쓴다.

## 1. 작업 시작 전

상태와 지금 브랜치를 확인하고 이번 작업 전부터 있던 사용자 변경과 이번 작업이 만든 변경을 가른다. 작업 중에 내가 손대지 않은 파일이 바뀌면 그 파일에서 손을 떼고 사용자에게 알린다. 그 파일이 이번 일에 필요하면 어떻게 할지 묻는다.

커밋 직전에 브랜치와 HEAD 가 시작 때와 같은지 다시 본다.

## 2. 복구 기준점

대량 이름 바꾸기·옮기기, 스키마·자료 이전, 위험한 리팩터링, 자동 대량 편집 전에 되돌릴 기준점을 둔다.

- 변경 없는 작업 트리: 기준 커밋이나 브랜치
- 변경 있는 작업 트리: 사용자 변경을 보존한 별도 브랜치·작업 사본·사본
- 아직 Git이 아님: 안전한 파일 백업 뒤 Git 초기화를 검토

버전 관리가 없는 폴더는 변경 크기와 상관없이 고치기 전에 바꿀 파일의 사본을 남긴다. 비밀 파일(`.env`, 키, 토큰 파일)은 파일 전체 사본 대신 바꿀 항목의 원래 줄만 값을 출력하지 않고 따로 기억해 둔다. 복구는 보존할 사용자 변경을 먼저 확인하고 필요한 파일·변경 조각만 골라 되돌린다.

복구 기준점을 둔 변경, 자료·실행 상태나 버전 관리 밖 설정을 바꾼 변경, 버전 관리가 없는 폴더의 변경은 끝에 되돌리기 확인과 되돌리는 법을 「확인」 줄에 적는다. 해 본 것 가운데 높은 층 하나를 쓴다.

- 복원해 봄: 백업에서 사본이나 시험 환경에 되살려 봄. 비밀 파일은 기억해 둔 항목만 되돌려 이름과 줄 수로 확인한다.
- 패치 확인: 차분이 거꾸로 적용됨.

자료·실행 상태나 버전 관리 밖 설정을 바꾼 변경은 복원해 봄까지 한다. 하지 못했으면 「못 한 것」에 까닭을 적는다.

## 3. 커밋 꼴

다음 차례에서 처음 있는 것을 쓴다.

1. 저장소에 적힌 형식(규칙 문서·기여 안내)
2. 커밋 이력이 되풀이해 보여 주는 형식. 「추정」 관례로 밝힌다.
3. 규칙 문서 「폴더 틀」 절의 `틀:` 줄이 고른 틀의 커밋 꼴
4. `<type>(<scope>): <summary>`. type 은 `feat`, `fix`, `docs`, `refactor`, `test`, `perf`, `build`, `ci`, `chore`, `revert`.

요약은 무엇이 달라졌는지, 본문은 왜 그렇게 했는지를 쓰고 요약을 되풀이하지 않는다. 버그 고침 커밋의 본문에는 확인된 원인과 재현 명령을 적는다. 배포 명령이나 판 번호 자리가 바뀌면 규칙 문서의 실행·시험 명령 절도 같은 변경에서 고친다.

서식 변경, 리팩터링, 동작 변경은 서로 다른 커밋으로 나눈다. 100줄 안팎이면 읽고 되돌리기 쉽고, 1000줄을 넘으면 나눈다. 올리기 전에 커밋 순서를 읽는 순서로 다듬는다.

## 4. 스테이징과 커밋 전 확인

- 의도한 파일과 변경 조각만 스테이징한다. 입력을 기다릴 수 없는 셸에서는 확인한 조각만 담은 패치 파일을 만들어 `git apply --cached <패치 파일>`로 올린다. 대화형 `git add -p`는 사람이 직접 할 때만 쓴다.
- 저장소 변경 전체가 이번 논리 단위이고 전체 차이를 검토했으면 `git add -A`를 쓴다.
- 커밋 전에 저장소의 CI 정의에서 지금 환경에서 되는 검사를 찾아 돌린다. 돌리지 못한 검사는 「못 한 것」에 적는다.

## 5. 원격 반영과 태그

- 커밋을 맡긴 범위에서는 단위 하나가 확인을 통과할 때마다 로컬 커밋을 저장점으로 남긴다. 다음 변경이 깨지면 마지막 저장점을 기준으로 이번 작업의 변경만 되돌려 원인을 조사한다.
- 올리라고 하면 원격의 앞선 커밋을 먼저 받아 합치고, 합친 상태에서 시험을 다시 돌려 통과한 뒤 올린다.
- 릴리스 태그는 확인을 마친 커밋에 붙이고, 붙이기 전에 판 번호·태그·변경 기록이 같은 값인지 대조한다. 이미 원격에 올린 태그를 옮기거나 지우는 일은 이력 다시 쓰기와 같은 기준으로 다룬다.
