# 릴리스와 전달

프로젝트의 기존 커밋·빌드·배포 방식으로 시킨 범위까지만 반영하고, 실제 반영 결과와 되돌릴 길을 확인한다.

## 함께 여는 스킬

이 스킬을 열면 아래 조건에 맞는 스킬을 일을 시작하기 전에 바로 함께 연다.

- 실행용 bat 파일을 만들거나 패키지 판을 올리거나 출시 전 의존성 감사를 할 때, 커밋할 때: `lion-dev-checks`

## 바로 할 일

1. 시킨 범위를 정한다. 커밋·push·태그·PR·병합·배포는 사용자가 시킨 것만 한다. 커밋을 시켰으면 커밋에서 멈춘다.
2. 규칙을 찾는다: 프로젝트 규칙 문서·README·최근 커밋·빌드 설정에서 커밋 꼴, 브랜치 규칙, 판 번호 자리, 빌드·배포 명령을 찾아 그대로 따른다.
3. 상태를 본다: 현재 브랜치, 바뀐 파일, 이번 작업 전부터 있던 사용자 변경. 사용자 변경은 보존하고 이번 작업의 변경만 다룬다.
4. 커밋 하나에 설명할 수 있는 변화 하나와 그 확인을 담는다. 스테이징한 차이에서 비밀값·환경 파일·디버그 흔적을 확인하고, 지금 환경에서 돌릴 수 있는 검사를 돌린 뒤 커밋한다.
5. 대량 이름 바꾸기·옮기기·자료 이전·되돌리기 어려운 배포 앞에는 복구 기준점을 만든다.
6. 빌드·배포는 소스 상태 → 빌드 입력 → 산출물 → 대상 환경 반영을 따로 대조한다. 닿을 수 없는 환경의 상태는 완료로 적지 않고 확인 못 함으로 적는다.
7. 비밀값·서명 재료는 허용된 환경에서만 쓰고 로그·산출물·출처 기록에 넣지 않는다. 사용자가 넣어야 하는 비밀값은 넣을 파일·환경 변수 이름만 알리고 대화로 받지 않는다.
8. 사용자가 직접 할 단계(서명 키 등록, 호스팅·스토어 설정 화면)는 여는 주소 · 누를 곳 · 받을 값 · 넣을 자리 순서로 쓴다. 지금 화면을 확인하지 못한 메뉴 경로는 공식 문서로 확인하거나 모른다고 쓴다.
9. 이력 다시 쓰기·파괴적 reset·강제 push·새 외부 전송은 명시한 승인과 복구 근거가 있을 때 한다. 기존 정책에 없는 출시 체계나 자동화는 요청받은 범위에서만 만든다.
10. 배포 중 실패하면 기존 복구 정책과 확인한 복구 경로를 따른다.
