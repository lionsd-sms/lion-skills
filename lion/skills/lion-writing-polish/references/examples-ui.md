# 전후 예: 커밋 메시지·화면 문구

괄호 속 숫자는 티 목록의 번호다. 예마다 지킨 것과 보고에 적은 것을 함께 둔다.

## 커밋 메시지

저장소의 기존 커밋이 접두어 없이 '~한다'로 끝나고, 바뀐 내용(diff)이 저장 버튼 문구와 목록 정렬이라고 하자. 커밋 메시지를 다듬을 때 바뀐 내용은 원문 자료로 본다.

고치기 전:

> ✨ feat: 사용자 경험 향상을 위한 다양한 UI 개선 사항 적용 및 코드 리팩토링 진행

고친 뒤:

> 저장 버튼 문구를 '확인'으로 바꾸고 목록을 이름순으로 정렬한다

- 고친 것: 이모지(24), 사용자 경험 향상(16), 다양한(2), 적용 및 진행(4), 리팩토링(22, 바뀐 내용에 구조 변경이 없어 지움).
- 지킨 것: 저장소 커밋 꼴(접두어 없음, '~한다').
- 저장소가 'feat:' 같은 접두어를 쓰면 접두어를 남긴다. 본문은 검토자가 1분 안에 읽을 길이로 쓰고, 긴 기록·표는 링크로 둔다.

## 화면 문구

오류 문구, 고치기 전:

> 앗! 저장하는 과정에서 문제가 발생했어요 😢 인터넷 연결 상태를 확인하신 후 다시 시도해 주시기 바랍니다!

고친 뒤(기존 화면이 해요체일 때):

> 저장하지 못했어요. 인터넷 연결을 확인한 뒤 다시 저장해 주세요.

- 고친 것: 감탄과 이모지(24·27), 과정에서 문제가 발생(4), 해요·바랍니다 섞임(29), 다시 시도 → 실제 동작 이름.
- 지킨 것: 원인 안내(인터넷 연결), 할 일(다시 저장).
- 오류 문구는 무엇이 안 됐는지, 알려진 원인, 할 일 순서로 쓴다. 버튼은 짧은 동작 이름(저장, 다시 저장)으로 쓴다.

양식 칸, 고치기 전:

> 상위 장비는 장비 2이며 현재 연결된 상태입니다.

고친 뒤:

```text
상위 장비    장비 2
상태         연결됨
```

- 설정·상태·입력 폼처럼 값을 비교하는 자리는 고정 이름표 + 값으로 쓴다. 알림·오류 원인처럼 문장 자체가 사건을 전하는 자리는 문장으로 쓴다.

확인창, 고치기 전:

> 주의하세요! 삭제하시겠습니까?

고친 뒤:

> 장비와 저장된 기록을 삭제하시겠습니까? 이 작업은 취소할 수 없습니다.

- 고친 것: '주의하세요'는 정보가 없어 지우고, 무엇이 사라지는지 쓴다.
- 확인창에는 사용자가 판단할 결과를 쓴다. 기록 없이 목록에서만 빠지면 '장비를 목록에서 삭제하시겠습니까?'로 쓰고, 복구되지 않는 자료까지 사라질 때만 취소할 수 없다는 문장을 붙인다.
